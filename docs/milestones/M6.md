# Part 1 — Milestone Overview

## Production goal

At the end of M6, sections are conceptually and visually replaced by **buckets** — flat containers of up to 5 children that are independent of class and grade. The Structure tab is renamed "Buckets," Subject and Program disappear as user choices (Subject stays visible as a static "Foundation" label), and volunteer count per slot-class relaxes from strict 1-2 to a flexible 1-5. Under the hood, the schema barely changes: one column added, two columns made nullable, no tables dropped, no data destroyed.

The pivot is mostly a UI re-skin plus a relaxation of validation rules and a small set of new invariants around class assignment and bucket membership. The `child_subject` table is retained (not dropped as originally proposed) so that any downstream Dots consumer that reads it keeps working. The `school_volunteer` lifecycle is not touched by M6 application code — that responsibility already moved to M8a's realtime sync.

## What does NOT ship in M6

Hard out-of-scope. Don't build any of these in M6 even if asked.

- **A dedicated move-child-between-buckets flow.** v1 ships with remove-and-add. If usability feedback demands a single-action move, that becomes a fast-follow.
- **Reordering buckets on the Buckets tab.** Alphabetical / creation-order only.
- **Multi-bucket assignment for a single child.** One bucket per child, enforced.
- **Class-tag on buckets.** Buckets are class-agnostic from the start. No class dropdown in Add/Edit Bucket, no class label on bucket cards. (This existed as a "drift found during build" item in the earlier draft — since the build never happened, it is simply the correct design from day one. See decision #1.)
- **Automatic re-population of `child_subject` when a bucket's `class_section_subject` set changes.** M6 idempotently inserts on child-to-bucket add; deeper synchronisation is out of scope.
- **Removing the Program table or the Subject table from the schema.** Both stay; only the UI stops asking for them.
- **Backfilling legacy `section_name` values into slug form.** Legacy rows are grandfathered — the slug unique constraint applies to new writes only.
- **A dedicated Bucket-Move screen or history view.** Bucket assignment history is not surfaced anywhere in the UI.
- **Bucket capacity beyond 5.** Max children per bucket remains 5, per R1.
- **Volunteer count beyond 5.** Max volunteers per slot-class is 5, and only up to the count of active children in the bucket.

> If something here turns out to be unexpectedly needed for M6, talk to the human first before adding scope.

## Key architectural decisions for M6

**1. Buckets are class-agnostic.** No class-tag on buckets in the UI — not in Add/Edit Bucket modals, not on bucket cards. Buckets can hold children from any class. The `class_section.school_class_id` column is retained purely for backward compatibility with legacy (pre-M6) rows — new buckets always leave it null.

**2. `child_subject` is retained, not dropped.** Rows are created idempotently on child-to-bucket-add (`get_or_create` on `(child_id, class_section_subject_id)`). Rows are never deleted, even when a child is removed from a bucket. This preserves historical data for any Dots consumer and removes the coordination need with the data platform team.

**3. Subject stays visible in the UI as a read-only "Foundation" label.** The Subject picker is removed from Add/Edit Slot-Class modals. In its place, a static "Subject: Foundation" text label appears. Legacy slot-classes with actual DB subject values of "Foundation Day 1" or "Foundation Day 2" still display as "Foundation" in the UI — the UI normalizes, but the DB values are preserved for Dots.

**4. `section_name` becomes a normalized slug; `section_display_name` holds the user's original input.** User types "Care Monster" → server stores `section_name = "care_monster"` and `section_display_name = "Care Monster"`. Slug is unique within a school (enforced by DB partial unique index). Display name is what shows on all UI. Legacy `section_name` values are grandfathered without normalization.

**5. `child_class` one-active-per-child is enforced at the service layer only, not the DB.** No DB partial unique index is added for this invariant (an earlier draft of this plan considered adding one via a migration and then dropping it — going straight to service-layer-only saves a throwaway migration). The `edit_child` service uses `select_for_update()` on the child row to serialise concurrent class changes, which is sufficient. This matches the project's convention (per `BUSINESS_RULES.md`) that business-rule enforcement lives in the service layer.

**6. R-bucket invariant blocks child removal when it would leave a slot-class over-volunteered.** Concretely: if a bucket has 3 children and a scheduled slot-class with 3 volunteers, removing a child is blocked with a clear error message. CO must remove a volunteer from the slot-class first.

**7. Volunteer count per slot-class is 1-5, bounded by active children in the bucket.** No slot-class can be created or edited with more volunteers than the bucket has active children. Enforced on slot-class create, slot-class edit, and child-remove-from-bucket.

**8. Foundation Subject is looked up by name from a seeded row.** A data migration ensures a `Subject` row with `subject_name="Foundation"` exists. The `create_slot_class` service reads this row and uses it for every new `ClassSectionSubject`. The row is cached at module load (safe because it never changes at runtime).

**9. Bucket assignment is optional at child creation; class assignment is mandatory.** `POST /children/` accepts `school_class_id` (required) and `class_section_id` (optional). Bucket assignment happens later through the Manage Bucket Children screen. A child in no bucket is "Unassigned."

**10. All existing data is grandfathered.** No migration destroys anything. Legacy `class_section` rows keep their `school_class_id` FK (invisible in UI). Legacy `section_name` values keep their non-slug form (unique index applies only to new writes). Legacy slot-class subjects keep their DB value (UI shows "Foundation" regardless). Existing `child_subject` rows stay readable.

### Slug normalization helper

`sessionops/services/sections/slug.py`:

```python
import re
from sessionops.exceptions import ValidationError

def normalize_section_slug(display_name: str) -> str:
    s = display_name.strip().lower()
    s = re.sub(r'[^a-z0-9]+', '_', s)
    s = s.strip('_')
    if not s:
        raise ValidationError("Bucket name must contain at least one letter or digit.")
    return s

def next_default_display_name(school_id: int) -> str:
    from sessionops.models import ClassSection
    n = ClassSection.objects.filter(
        school_id=school_id, is_active=True, removed=False
    ).count()
    return f"Group {n + 1}"
```

**Examples:**
- `"Care Monster"` → `care_monster`
- `"Group 1"` → `group_1`
- `"5th - D"` → `5th_d`
- `"   spaces   "` → `spaces`

## F-M6-3 — Bucket-children add/remove endpoints

**Status:** Built. 22 new tests passing (14 unit + 8 API integration), plus F-M6-2 and legacy section regression (49 tests) unaffected. See `docs/milestones/plans/F-M6-3-tasks.md` for full execution log.

**Goal:** Two new endpoints for managing bucket membership after child creation. Enforce R1 (max 5), R-bucket-membership (one bucket per child), and R-bucket (volunteers ≤ children on removal). Populate `child_subject` idempotently on add; never delete on remove.

### Endpoints

| Method | Path | Purpose |
|--------|------|---------|
| POST | `/api/schools/{school_id}/sections/{section_id}/children/` | Add existing child to bucket. Body: `{ child_id: int }` |
| DELETE | `/api/schools/{school_id}/sections/{section_id}/children/{child_id}/` | Remove child from bucket |

### `add_child_to_bucket` flow

1. `select_for_update` on `ClassSection` (validate bucket active, belongs to school)
2. `select_for_update` on `Child` (validate active, belongs to school)
3. R1 check: count active `ChildClassSection` rows for bucket < 5
4. R-bucket-membership check:
   - If child has an active `ChildClassSection` in another bucket → `ConflictError` with existing bucket's display name
   - If child is already in this bucket → idempotent no-op, return existing row
5. Create `ChildClassSection(child_id, class_section_id)`
6. For each active `ClassSectionSubject` on this bucket, `ChildSubject.objects.get_or_create(child_id, class_section_subject_id)` — idempotent

### `remove_child_from_bucket` flow

1. Validate bucket + child + membership
2. R-bucket check: for each active `SlotClassSection` on this bucket, count(volunteers) must be ≤ (count(active children in bucket) - 1). If any slot-class would break the invariant, raise `ConflictError` with message:
   > "Cannot remove child. A scheduled slot-class for this bucket has N volunteers and would have only M children. Remove a volunteer from the slot-class first."
3. Soft-delete `ChildClassSection` (`is_active=False, removed=True, deleted_at=now`)
4. **Do NOT touch `ChildSubject` rows** — retained for historical query.

### Schemas

```python
class BucketChildAddIn(Schema):
    child_id: int

class BucketChildOut(Schema):
    child_class_section_id: int
    child_id: int
    class_section_id: int
```

### Business rules enforced

- **R1:** Max 5 active children per bucket.
- **R-bucket (NEW):** count(volunteers) ≤ count(active children) after removal.
- **R-bucket-membership (NEW):** One active bucket per child.
- **R9:** Soft-delete only.

### Test scenarios

- Happy path: add child to empty bucket → `ChildSubject` rows created idempotently
- Edge case: add 6th child to a full bucket → 400/409, R1 enforced
- Edge case: add child already in another bucket → 409 naming the existing bucket
- Error case: remove child that would leave a 3-volunteer slot-class with 2 children → 409 with the exact guidance message
- Idempotency: adding the same child to the same bucket twice → second call is a no-op, no duplicate rows

### Post-M6 bug found and fixed: R-bucket only enforced on ONE of three child-removal paths (2026-07-24)

**Found:** `remove_child_from_bucket` (above) enforces R-bucket correctly. But two sibling code paths that soft-delete the same `ChildClassSection` row never called into it: `services/children/deactivate.py::deactivate_child` (full child deactivation — bulk `.update()`s `ChildClassSection` with zero check) and `services/children/edit.py::edit_child`'s bucket-reassignment branch (moving a child to a different bucket — checks capacity on the *destination* bucket but never on the bucket being vacated). Net effect: deactivating a child, or editing which mentoring circle a child belongs to, could silently leave a scheduled slot-class over-volunteered with no error, no warning, and no reactive mechanism (no signals, no Celery tasks exist in this codebase) to ever catch or repair it afterward.

**Fixed:** extracted the check itself out of `remove_child_from_bucket` into a shared `assert_bucket_not_over_volunteered(bucket, excluding_child_class_section_id)` (still in this file) — one copy of the logic, three callers. Wired into `deactivate_child` (locks the child's current bucket via `select_for_update()` before the existing bulk soft-delete, right after the RBAC check) and into `edit_child`'s bucket-change branch (locks and checks the *old* bucket being vacated, before the existing destination-capacity check on the new bucket). Both raise the same `ConflictError` (409) `remove_child_from_bucket` already did — hard block, no auto-remediation of volunteers, by design (matches existing behavior everywhere else this rule applies).

**Why the lock matters:** without `select_for_update()` on the bucket, two concurrent requests touching the same bucket can both read "capacity OK" before either commits (a lost-update race under READ COMMITTED) and both proceed, landing in a genuinely over-volunteered state neither request ever saw. Lock order is consistent everywhere this rule is checked: bucket locked before any `ChildClassSection` write; in `edit_child`, vacated-bucket-then-destination-bucket (a fixed convention — worth keeping if a future function ever needs to lock two buckets at once).

**Tests:** four new tests added to `test_bucket_children.py` (not the children-specific test files, which have no slot-class/volunteer fixtures) — `TestDeactivateChildRBucket` and `TestEditChildRBucket`, covering the blocked and normal-success case for each function, reusing the existing `_make_slot_class_with_volunteers` etc. fixtures.

See `docs/BUSINESS_RULES.md`'s R-bucket entry (updated same day) for the canonical rule text.

**2026-07-25 — message clarity follow-up:** the `ConflictError` message now names both the bucket and the specific slot, instead of just "this bucket": `Cannot remove child from bucket "{bucket_name}". A scheduled slot-class on slot "{slot_name}" has {vol_count} volunteers and would have only {remaining_children} children. Remove a volunteer from the slot-class first.` Requires `.select_related("slot_id")` on the `active_slot_classes` query (added) to avoid an N+1 per over-volunteered slot-class. Also added an (i) info icon next to the "Volunteers" label in both `AddSlotClassModal.tsx` and `EditSlotClassModal.tsx` (same `Tooltip`+`Info`-icon pattern as the Mentoring Circles section header, see the earlier "Bucket renamed to Mentoring Circle" note above) explaining the rule up front: a mentoring circle holds up to 5 children, a slot-class holds up to 5 volunteers, but volunteers can never exceed the mentoring circle's active children.

## F-M6-4 — Child enrollment decoupling + child_class invariant

**Status:** Built. `enroll_child`/`edit_child`/`reactivate_child` rewritten per plan; `ChildOut.current_section`/`current_school_class` + `list_children(unassigned=...)` contract delivered for F-M6-7. ### `enroll_child` flow (rewritten)

1. Validate `school_class_id` — must exist, belong to this school
2. If `class_section_id` provided: validate bucket, `select_for_update`, check R1 capacity
3. School capacity check (unchanged from M2)
4. SAY resolution (unchanged)
5. Create `Child`
6. **Always** create `ChildClass` from `payload.school_class_id` (not derived)
7. If bucket provided: create `ChildClassSection` + idempotent `ChildSubject` for each active `ClassSectionSubject`
8. `BatchChild` + `ChildProgram` (unchanged)

### `edit_child` — class change path (new)

When `payload.school_class_id` is provided and differs from the current active `ChildClass`:

1. **Pre-check invariant guard:** count active `ChildClass` rows for this child. If > 1, raise `ValidationError("Data inconsistency: multiple active class assignments for this child. Contact an administrator.")` — belt-and-braces guard even though `select_for_update` on Child + service serialisation should prevent this.
2. Validate new `SchoolClass` belongs to this school
3. Atomic swap: soft-delete old `ChildClass` row, insert new `ChildClass` row

### `edit_child` — bucket change path (updated)

- Section change block preserved from M3
- `ChildSubject` re-population: `get_or_create` loop, no bulk_create
- **Old `ChildSubject` rows are NOT soft-deleted** — retained for history

### Business rules enforced

- **R1:** Bucket capacity on enroll.
- **R-class (NEW):** One active `ChildClass` per child — enforced at the service layer only via `select_for_update` + atomic transaction.
- **R9:** Soft-delete on class swap. `ChildSubject` rows never deleted.

### R-class enforcement architectural note

Per decision #5, no DB partial unique index backs this invariant — enforcement is service-layer-only, matching the project convention that business rules live in services. The `select_for_update` on the Child row serialises concurrent class-change calls, so no race condition can create two active `ChildClass` rows. The `count(active_cc) > 1` pre-check is a data-quality guard for pre-existing inconsistent state, not a race prevention.

### Backend contract check for F-M6-7

`ChildItem` response must include `current_section` (nullable: `class_section_id`, `section_display_name`, `section_name`) and `current_school_class` (`school_class_id`, `class_name`). `list_children` must accept an `unassigned: bool` query param (or treat `section_id=0` as "unassigned"). Build these as part of this feature — F-M6-7 depends on them and there's no reason to defer.

### Test scenarios

- Happy path: enroll child with class only (no bucket) → `Child` + `ChildClass` created, no `ChildClassSection`
- Happy path: enroll child with class + bucket → all rows created, `ChildSubject` idempotent
- Edge case: edit child's class → old `ChildClass` soft-deleted, new one created, exactly one active row after
- Error case: edit with `school_class_id` belonging to a different school → 400
- Data-quality guard: seed a child with 2 active `ChildClass` rows directly in DB, attempt edit → clear error, no silent overwrite

### Post-M6 regression found and fixed: class deletion no longer guarded correctly

**Found:** After this feature shipped, `soft_delete_school_class` (F-M2-4, `services/structure/queries.py`) was never updated to match the decoupling. It still blocked class deletion by counting active `ClassSection` rows with `school_class_id` pointing at the class — but per decision #1, buckets never set `school_class_id`, so that count is always 0 for any post-M6 bucket-based school. Meanwhile, F-M6-4 made class assignment a direct `ChildClass` link, entirely independent of sections/buckets. Net effect: a class with active enrolled children (linked only via `ChildClass`, zero sections) could be deleted with no error, silently orphaning those children's class assignment — the exact hazard R9/soft-delete conventions are meant to prevent.

**Fixed:** `soft_delete_school_class` now counts active `ChildClass` rows for the class instead of `ClassSection` rows, raising the same `ConflictError` (409) shape but with a children-count message: `"Cannot remove class: N active child(ren) enrolled. Remove or reassign them first."` A legacy `ClassSection` still pointing at the class (grandfathered per decision #10) no longer blocks deletion on its own — only active children do, consistent with buckets being class-agnostic everywhere else.

**Tests:** `tests/test_f_m2_4_classes.py` — replaced `test_soft_delete_class_with_active_sections_raises_conflict` (encoded the stale behavior) with `test_soft_delete_class_with_active_children_raises_conflict`, and added `test_soft_delete_class_with_legacy_section_but_no_children_succeeds` as an explicit regression guard against reintroducing the old section-based check. Full backend suite re-run to confirm no other consumer depended on the old behavior. See `docs/milestones/M2.md`'s F-M2-4 section for the corrected business rule.

def _resolve_volunteer_list(volunteer_ids, school_id, slot, user):
    volunteers = []
    for vid in volunteer_ids:
        vol = User.objects.get(user_id=vid, is_active=True)

### Post-M6 (2026-07-28): volunteer-only edit no-op fix

**Bug:** `edit_slot_class`'s volunteer-only branch decided `vols_changing` from field *presence* alone (`new_volunteer_ids is not None`), not from whether the list actually differed from the current assignment. An edit form that resubmits its current `volunteer_ids` on every save (normal for a form that always sends its full state) triggered this branch every time — even when nothing changed — unconditionally soft-deleting every active `SlotClassSectionVolunteer` row for the slot-class and creating fresh replacement rows with identical volunteer IDs. Effect: every no-op "Save" on the edit modal wrote a spurious removal+reassignment into the volunteer-assignment audit trail (`deleted_at` on old rows, new `created_at` on "new" rows), and needlessly re-ran `check_r_bucket_capacity`, `check_r4_volunteer`, `validate_volunteer_worknode_match`, and the R6 same-slot check.

**Fix:** compute `old_vol_ids` first and compare `set(new_volunteer_ids) == set(old_vol_ids)` before doing anything else in the volunteer-only branch; if equal, return immediately with no writes. Order of the submitted list doesn't matter. Scoped to the pure volunteer-only-edit branch (section unchanged) — the section-changing branch's volunteer recreation was left as-is, since that path already does a full cascade reset for other reasons and wasn't the reported issue.

## Validation rules — final state

| Rule | Current | After M6 |
|------|---------|----------|
| R1: Max children per bucket | 5 | 5 (unchanged) |
| R2: Volunteer count per slot-class | 1-2 | **1-5** |
| R3: Volunteer uniqueness in slot-class | vol1 ≠ vol2 | **All volunteers in `volunteer_ids` must be unique** |
| R4: One volunteer = one school | Enforced via school_volunteer (M6 does not write; M8a does) | Unchanged semantics |
| R5: Same bucket not twice in same slot | Enforced | Unchanged |
| R6: Volunteer not in two slot-classes in same slot | Enforced | Unchanged (extended check to full volunteer list) |
| R7: No overlapping slots same school same day | Enforced | Unchanged |
| **R-bucket (NEW)** | n/a | count(volunteers) ≤ count(active children in bucket); enforced on slot-class create, slot-class edit, and child-remove-from-bucket |

| **R9: Soft-delete only** | Enforced everywhere | Unchanged. `ChildSubject` explicitly retained (never deleted). |

## Migration / rollout plan

Order matters. Backend migrations apply first, then backend code deploys, then frontend deploys, then smoke tests.

1. **Pre-flight (staging):** Run the pre-flight query (class_section slug collision check). Confirm zero rows.
2. **Apply migration 0024** — nullable fields on class_section.
3. **Apply migration 0025** — section_display_name + backfill.
4. **Apply migration 0026** — class_section slug unique per school.
5. **Apply migration 0027** — seed Foundation Subject row.
6. **Deploy backend** — services and endpoints for F-M6-2 through F-M6-5.
7. **Deploy frontend** — F-M6-6 (Buckets tab). F-M6-7 and F-M6-8 deploy incrementally as built.
8. **Smoke test in production:** create bucket with a spaced display name → confirm slug derivation. Add cross-class children → confirm bucket accepts. Schedule into a slot with 5 volunteers → confirm R-bucket + R2 relaxed. Verify Dots row generated correctly. Verify `child_subject` populated idempotently.

### Rollback

All migrations are reversible:
- 0027 reversal: delete the seeded Foundation Subject (safe — no FK references break because M6 code will be rolled back too)
- 0026 reversal: drop the slug unique index
- 0025 reversal: drop `section_display_name` column
- 0024 reversal: `ALTER COLUMN ... SET NOT NULL` (only if no null values — new buckets without class link would prevent this; roll back frontend first)

Frontend can be reverted independently of backend. If M6 is fully rolled back, all existing data continues to function under the M3 model with no loss.
