# Feature Plan: F-M7-1 + F-M7-2 — Migration Loader Endpoints + Mode Suppression

Planned together because F-M7-2 ("migration mode suppression") is not a separable surface in this codebase — it's a property of how F-M7-1's endpoints are built, not a second set of endpoints. There is no F-M7-2-only work.

---

## Overview

Build 20 internal POST endpoints (`/api/internal/migrate/{table}/`) that accept one Bubble-shaped row at a time and upsert it into Session-Ops using the row's own PK, authenticated by a dedicated service token instead of user JWT. These are the landing pads for the n8n workflows (F-M7-5 through F-M7-9) that the data platform team builds on top of dbt models (F-M7-3) and Hasura REST endpoints (F-M7-4) — none of that is in scope here; this plan covers only the Session-Ops backend surface.

**`subject` is out of scope** (confirmed): M6's migration `0027_m6_seed_foundation_subject` already seeds a fixed `Subject` row and the table only ever holds ~2-3 rows. `class_section_subject`'s `subject_id` FK resolves against whatever `Subject` rows already exist — no dedicated loader endpoint for it. This is the same shape as `partner`/`user`/`partner_worknode` being external preconditions, just smaller: `subject` must be populated (by M6's existing seed, or manually if more variants are needed) before `class_section_subject` rows can load.

**`child_removal_log` added (found 2026-07-15):** a full audit of every model in `sessionops/models/` (28 classes) turned up one genuine gap — `ChildRemovalLog` is real Bubble-sourced attrition-history data (one row per child-removal event) that every earlier draft missed. It's the only table here with no `created_by`/`updated_by` fields, so the migration-bot-user question (Open Questions #1) doesn't apply to it. Everything else not on this list (`password_reset_tokens`, `realtime_sync_log`, `sync_run`, `user_auth`) is Session-Ops-internal, generated by Session-Ops itself, with no Bubble source — correctly excluded, not gaps.

The key design decision this plan makes (and the milestone doc left ambiguous): **loader endpoints do not call the existing enrollment/scheduling services** (`enroll_child`, `create_bucket`, `create_slot`, `create_slot_class`). They do a direct, generic ORM upsert instead. See "Key design decision" below for why — it's not a simplification, it's a correctness requirement.

## High-Level Design (HLD)

### Data flow

```
n8n → POST /api/internal/migrate/{table}/  (Authorization: Bearer <MIGRATION_SERVICE_TOKEN>)
    → migration_api.py router validates token, parses body against the table's Pydantic schema
    → services/migration/generic.py::migrate_row(TABLE_CONFIGS[table], payload)
        1. Resolve required FKs (real DB FKs + decision #15 raw-int "school_id" checks) — miss → 422 orphan_fk, row skipped
        2. Resolve optional FKs — miss → set null, add warning
        3. Explicit-PK create-or-update via ORM, created_by/updated_by = Migration Bot user
        4. Return (status, changes, warnings)
    → router maps result to the 201/200/422/400/500 envelope the milestone spec defines
```

### Key architectural decision: generic upsert, not 20 bespoke service files, not existing-service reuse

**Why not reuse `enroll_child`, `create_bucket`, `create_slot_class`, `create_slot`:** I read all four. `enroll_child` (`services/children/enroll.py`) doesn't just validate — it *orchestrates*: one call creates `Child` + `ChildClass` + optionally `ChildClassSection` + idempotent `ChildSubject` rows + `BatchChild` + a **hardcoded** `ChildProgram` row (`FOUNDATION_PROGRAM_ID = 1`, unconditional). M7 migrates `child`, `child_class`, `child_class_section`, `child_subject`, `batch_child`, and `child_program` as **six independent tables**, each with its own Bubble source and its own loader endpoint. Calling `enroll_child` during migration would silently overwrite real Bubble history with `enroll_child`'s hardcoded assumptions (e.g., every migrated child gets Foundation Program regardless of what Bubble's `child_program` data actually says) and would create rows through a side channel that F-M7-8's separate `child_program`/`batch_child` loaders would then also try to create — double-inserts or silent divergence. Same class of problem applies to `create_bucket` (recomputes the slug from a display name — but decision #16 already has dbt computing the slug) and `create_slot_class`/`create_slot` (enforce R2/R3/R4/R5/R6/R7/R-bucket inline, which is exactly what migration mode needs to *not* do per-row).

This resolves the spec's own ambiguity: F-M7-2's narrative describes an `enforcement_mode` parameter threaded through existing services; F-M7-1's own code sample instead shows direct `Child.objects.create(**payload)`. The direct-ORM approach is correct — not just less risky.

**Why one generic function instead of 20 files:** every one of the 20 tables reduces to the same shape — explicit-PK upsert, a small list of required/optional FK checks (some real DB FKs, some raw-int checks per decision #15), and `created_by`/`updated_by` set to a fixed system user (except `child_removal_log`, which has neither field). A per-table Python file per the spec's illustrative `services/migration/migrate_child.py` naming would be ~20 near-identical files with copy-paste drift risk. Instead:

```python
# sessionops/services/migration/registry.py
@dataclass
class TableConfig:
    model: type[models.Model]
    pk_field: str                              # e.g. "child_id"
    required_fks: list[FkCheck]                 # orphan_fk -> 422, row skipped
    optional_fks: list[FkCheck]                 # orphan_fk -> null + warning
    immutable_on_update: set[str] = frozenset()  # fields never overwritten after first insert, if any

@dataclass
class FkCheck:
    field: str                 # payload/model field name, e.g. "school_class_id"
    kind: Literal["real_fk", "raw_int_to_partner"]  # raw_int_to_partner = decision #15 check
    target_model: type[models.Model] | None = None   # for real_fk
    target_field: str = "pk"

TABLE_CONFIGS: dict[str, TableConfig] = {
    "child": TableConfig(
        model=Child, pk_field="child_id",
        required_fks=[FkCheck("school_id", "raw_int_to_partner")],
        optional_fks=[],
    ),
    "school_class": TableConfig(
        model=SchoolClass, pk_field="school_class_id",
        required_fks=[
            FkCheck("school_academic_year_id", "real_fk", SchoolAcademicYear),
            FkCheck("class_id", "real_fk", Class),
            FkCheck("school_id", "raw_int_to_partner"),
        ],
        optional_fks=[],
    ),
    "class_section": TableConfig(
        model=ClassSection, pk_field="class_section_id",
        required_fks=[FkCheck("school_id", "raw_int_to_partner")],
        optional_fks=[FkCheck("school_class_id", "real_fk", SchoolClass)],  # M6: optional post-pivot
    ),
    # ... 17 more entries, one per table (full list in "Per-table FK map" below).
    # No "subject" entry — subject is not migrated (see Overview); class_section_subject's
    # subject_id FK check reads whatever Subject rows already exist (M6 seed + any manual additions).
}
```

```python
# sessionops/services/migration/generic.py
def migrate_row(config: TableConfig, payload: dict) -> MigrationResult:
    warnings = []
    for check in config.required_fks:
        if not _fk_exists(check, payload.get(check.field)):
            return MigrationResult(status="skipped", reason="orphan_fk", detail=f"{check.field} {payload.get(check.field)} does not exist")
    for check in config.optional_fks:
        val = payload.get(check.field)
        if val is not None and not _fk_exists(check, val):
            warnings.append(f"{check.field} {val} does not exist; setting to NULL")
            payload[check.field] = None

    pk_value = payload[config.pk_field]
    with transaction.atomic():
        existing = config.model.objects.filter(**{config.pk_field: pk_value}).first()
        bot = get_migration_bot_user()
        if existing:
            changes = []
            for field, new_val in payload.items():
                if field == config.pk_field or field in config.immutable_on_update:
                    continue
                if getattr(existing, field, None) != new_val:
                    setattr(existing, field, new_val)
                    changes.append(field)
            if changes:
                existing.updated_by = bot
                existing.save()
            return MigrationResult(status="updated" if changes else "updated", changes=changes, warnings=warnings)
        else:
            obj = config.model(**payload, created_by=bot)
            obj.save(force_insert=True)   # explicit PK preserved (Option A from the spec)
            return MigrationResult(status="inserted", warnings=warnings)
```

This is ~150 lines total instead of ~20 files × ~40 lines, and every table's behavior is declared as data (`TABLE_CONFIGS`), not duplicated logic. Adding a 21st table later (e.g. `subject`, if that decision changes) is a config entry, not a new file.

### What replaces per-row "business rule warnings"

The milestone spec's F-M7-2 table implies computing and returning a warning for every suppressed rule (R1, R2, R-bucket, etc.) on each row. Since loader endpoints never call the rule-enforcing services, they never evaluate those rules at all — recomputing them here would mean re-implementing R1/R2/R3/R5/R6/R7/R-bucket/R-class read-only checks a second time, purely for logging. **Recommendation: don't.** F-M7-10 (data quality gate, separate feature, already scoped to run post-migration cross-table assertions for exactly these rules — "8 children have >1 active child_class_section rows", "3 class_sections have >5 active children") is the right place for this. Per-row warnings in this feature stay limited to what the generic upsert already surfaces: optional-FK-nulled-out. Flagged in Open Questions for explicit confirmation since it's a real scope reduction from the spec's literal text.

### Auth

New file `services/migration/auth.py`, same shape as the existing `services/realtime_sync/auth.py`:

```python
import os
MIGRATION_SERVICE_TOKEN = os.getenv("MIGRATION_SERVICE_TOKEN", "")

def validate_migration_token(authorization_header: str) -> bool:
    if not MIGRATION_SERVICE_TOKEN:
        return False
    return authorization_header == f"Bearer {MIGRATION_SERVICE_TOKEN}"
```

Unlike M8a's internal sync endpoint (non-guessable path via `INTERNAL_SYNC_ENDPOINT_PATH`, dual admin-JWT-or-service-token auth), the M7 spec explicitly puts these at a fixed, predictable prefix (`/api/internal/migrate/`) secured by the token alone — no admin-JWT fallback, since there's no legitimate reason for a human to call these directly outside a manual test client. `auth=None` on the router, manual header check inside each route, same pattern as `realtime_sync_api.py::_resolve_auth` but simpler (token-only, no JWT branch).

### API endpoints

All 20 follow the exact same shape (auth via service token, not admin JWT):

```
POST /api/internal/migrate/{table-path}/
Authorization: Bearer <MIGRATION_SERVICE_TOKEN>
Body: single row, JSON, keys = Session-Ops column names, PK field present

201 -> {"status": "inserted", "table": ..., "pk": ..., "warnings": [...]}
200 -> {"status": "updated", "table": ..., "pk": ..., "changes": [...], "warnings": [...]}
422 -> {"status": "skipped", "table": ..., "pk": ..., "reason": "orphan_fk", "detail": ..., "action": "skip"}
400 -> {"status": "invalid", "table": ..., "pk": ..., "error": ..., "action": "skip"}   (schema/type validation failure)
500 -> generic Exception handler already in routes.py (IntegrityError etc.) -> workflow stops, per spec
```

**RBAC:** None in the traditional sense — no user role check, no `schools_visible_to()` scope filter. Auth is entirely the service-token check. This is deliberate (decision in the milestone spec): migration mode is not a user action, it has no RBAC scope because there's no acting user. The service-token check is the entire access control surface, which is why the spec insists on a separate token from M8a's and a URL prefix that's easy to grep in nginx logs.

### Migrations

None. `created_by`/`updated_by` on every migrated row is set to the existing real user `user_id=1924616` (`gaurav.thwait@makeadiff.in`), looked up directly — no seed migration needed.

## Business Rules Enforced

None of BUSINESS_RULES.md's R1-R8 rules are evaluated by these endpoints — that's the entire point of migration mode (decision #5 in M7.md). What **is** enforced, because it can't be suppressed:

- R9 (no hard deletes) — not applicable, loader only inserts/updates, never deletes.
- R10 (removal reason mandatory on child deactivation) — not applicable here; if Bubble's child row is already inactive, the loader just writes `is_active=False`/`removed=True` verbatim along with whatever `removed_reason` Bubble supplies (or null, which the DB allows since it's not enforced at the DB layer — R10 is service-layer-only per BUSINESS_RULES.md, and this loader bypasses the service layer by design).
- NOT NULL / unique / real FK constraints — enforced by Postgres regardless of migration mode; surfaces as 500 (IntegrityError) or 422 (orphan_fk, caught proactively before the INSERT).
- Decision #15 (raw-int `school_id`-style references) — enforced explicitly in `generic.py::_fk_exists` for the `raw_int_to_partner` check kind, since Postgres has no constraint to catch it.

## Security Review

- **Auth:** service-token only, `Authorization: Bearer <MIGRATION_SERVICE_TOKEN>`. No admin-JWT fallback (unlike M8a) — there's no legitimate human-driven use case for these endpoints outside manual testing during dry runs.
- **Token isolation:** `MIGRATION_SERVICE_TOKEN` is a distinct env var from `INTERNAL_SYNC_SERVICE_TOKEN` (M8a) per the spec — a leaked M8a token must not grant migration-mode write access, and vice versa.
- **No RBAC scope filtering** — intentional, not an oversight; there's no user to scope. Flagged here so a future reviewer doesn't mistake the absence of `schools_visible_to()` for a missed check.
- **Input validation boundary:** Pydantic schema with `extra="forbid"` catches unexpected fields (e.g. a dbt model renaming a column) as a 422 rather than silently dropping data.
- **Data exposure:** endpoints are write-only (accept row, return status/changes/pk — never return other rows' data). No enumeration risk since PK is supplied by the caller, not guessed.
- **Token rotation:** per the milestone spec, rotate `MIGRATION_SERVICE_TOKEN` after cutover completes (F-M7-11/12 territory, not this feature, but worth the reminder here since this is where the token is introduced).

## Testing Strategy

### Backend unit tests (service layer — `services/migration/generic.py`)

- `test_migrate_row_inserts_new_pk` — new PK, all required fields present → status=inserted
- `test_migrate_row_updates_existing_pk_with_changes` — existing PK, one field differs → status=updated, changes=[field]
- `test_migrate_row_idempotent_rerun` — same payload twice → second call returns updated with changes=[]
- `test_migrate_row_required_fk_missing_returns_skipped_orphan_fk`
- `test_migrate_row_optional_fk_missing_sets_null_and_warns`
- `test_migrate_row_raw_int_school_id_missing_returns_orphan_fk` (decision #15 — no DB constraint backs this, so this test is the only thing that catches a regression here)
- `test_migrate_row_sets_created_by_to_migration_bot_on_insert`
- `test_migrate_row_does_not_overwrite_created_by_on_update`
- `test_migrate_row_explicit_pk_preserved_not_autogenerated`
- One parametrized test running all 20 `TABLE_CONFIGS` entries through a minimal valid payload — catches config-registry typos (wrong model, wrong pk_field, FK target class mismatch) cheaply without 20 hand-written near-duplicate test files.

### Backend integration tests (API layer)

Per endpoint (or parametrized across all 20 given they share one router pattern):
- `test_endpoint_rejects_missing_auth_header` → 401 equivalent (or whatever the router's manual check returns — decide during build to match spec's response shapes, not the existing global 401 handler, since these routes use `auth=None`)
- `test_endpoint_rejects_wrong_token`
- `test_endpoint_accepts_valid_token_inserts_row` → 201
- `test_endpoint_accepts_valid_token_updates_row` → 200
- `test_endpoint_returns_422_for_orphan_required_fk`
- `test_endpoint_returns_400_for_schema_violation` (missing PK field, wrong type)
- At least 3 full end-to-end table tests exercising real FK chains: `children` (raw school_id check), `school-classes` (two real FKs), `slot-class-section-volunteers` (one row per volunteer, no vol1/vol2 special-casing needed at this layer since dbt already unpivots)

### Regression check (blast-radius verification)

- Run the full existing test suite for `children`, `structure`/`sections`, `slot_classes`, `slots` unchanged — since this feature deliberately does not modify `enroll_child`, `create_bucket`/`edit_bucket`, `create_slot_class`, `create_slot`, zero regressions are expected there. Explicitly run these suites as part of this feature's Definition of Done to confirm the "no existing services touched" claim holds.

### Manual verification

- Hit one endpoint with `curl` using a hand-built payload for `children` (has a raw-int FK check) and `school-classes` (has two real FKs) — confirm 201, then re-POST the same body — confirm 200 with `changes: []`.
- Confirm a bad `school_id` (no matching Partner) returns 422 `orphan_fk`, not a 500 or a silent insert.
