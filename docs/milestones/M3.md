# Part 1 — Milestone Overview

## Production goal

At the end of M3, a Community Officer can assemble the full teaching schedule for their schools:

1. See the Volunteers tab and Slots tab as active (no longer "Coming soon")
2. View the list of volunteers automatically populated from the Worknode platform (synced via Hasura), without any manual action
3. CHO users automatically see schools where their worknode_id is mapped via partner_worknode
4. Create weekly recurring slots (e.g., "Monday 11-12 AM at School X")
5. Edit and soft-delete slots
6. Compose slot-classes inside slots: section + subject + 1-2 volunteers
7. All scheduling business rules enforced (no overlapping slots, vol1 ≠ vol2, one volunteer one school, etc.)
8. View the full schedule for a school (slot-by-slot, with subject + section + volunteers)

The Volunteers tab and Slots tab are both active. The Calendar tab remains "Coming soon" (data layer is M4).

## What changed from the previous M3 spec (important — read this)

Volunteer management was redesigned in this revision:

- **No more manual volunteer assignment.** Volunteers are not added by a CO clicking "Add Volunteer." They appear automatically based on Worknode (MAD's user management platform) data, which is already the source of truth for who-is-tagged-where.
- **New schema additions:** `User.worknode_id` (synced from Hasura) and a new `partner_worknode` table (also synced from Hasura) that maps Session-Ops schools (Partners) to Worknode entries.
- **The Volunteers tab is read-only** for everyone in M3. It shows the list of users whose `worknode_id` matches the school's Worknode entry. No Add button, no Remove button.
- **`school_volunteer` table is kept.** It's still the source of truth for "this volunteer was tagged at this school" (history + de-dup for R4 enforcement). But insertion now happens implicitly during slot-class creation, not on the Volunteers tab. Soft-delete happens implicitly when the volunteer's last slot-class at that school goes away.
- **Volunteer removal feature moved to M5** (F-M5-12). User management is done on the external Worknode platform, not Session-Ops. M3 has no Remove UI.
- **`reporting_manager_user_login` is no longer used for M3 scope.** Worknode matching replaces it.

## What does NOT ship in M3

Hard out-of-scope. Don't build any of these in M3 even if asked.

- **Manual volunteer assignment / removal UI.** Auto-populated from Worknode. Removal moved to M5.
- **Session dates + holidays.** M4. Slots are pure weekly patterns; the system doesn't know about specific dates yet.
- **Calendar tab content.** M4 — date-level rendering. Tab stays disabled in M3 with "Coming soon".
- **Move volunteer between slot-classes flow.** M4. M3 has the building blocks (edit/delete slot-class) but no dedicated "move" UI.
- **Cross-school volunteer conflict detection.** M5. R4 enforces single-school assignment at slot-class creation.
- **Webhook receiver from Hasura.** M4. M3 relies on the cron sync from M1.
- **Per-date schedule view.** Out of M3 by design. Per-date views arrive when M4 adds holidays.
- **Volunteer-deactivation alerts from sync.** M4.
- **Year progression.** M5. M3 operates strictly within the active 2026-2027 year.
- **Recurring slot templates beyond a single weekly pattern.** Each slot is one weekly pattern.
- **Substitute volunteer workflow, performance metrics, slot capacity, attendance tracking.** All later.

> If something here turns out to be unexpectedly needed for M3, talk to the human first before adding scope.

## Key architectural decisions for M3

**1. Volunteers come from Worknode via `worknode_id` matching.** A volunteer is a User in the user table (synced from Hasura) who has a `worknode_id` matching one of the school's `partner_worknode` entries. Session-Ops does not maintain its own volunteer assignment UI; Worknode is the source of truth for who-is-tagged-where.

**2. `school_volunteer` table is the historical/de-dup record.** Even though display comes from worknode matching, the `school_volunteer` table is preserved for two reasons:
- History of which volunteers have ever been associated with a school (audit trail)
- R4 enforcement: when a CO assigns a volunteer to a slot-class, the system checks `school_volunteer` to ensure the volunteer isn't already actively assigned at a different school. Blocking happens at the slot-class create step, not on the Volunteers tab.

**3. `school_volunteer` rows are managed implicitly during slot-class CRUD.** No direct UI manipulation. Lifecycle:
- **Inserted** when slot-class create picks a volunteer who has no active `school_volunteer` row at this school.
- **Untouched** when slot-class edits swap volunteers within the same school (the leaving volunteer's row is removed only if they have no more slot-classes here).
- **Soft-deleted** when a volunteer's last `slot_class_section_volunteer` row at a school is removed (via slot-class delete, slot delete, slot-class volunteer swap, or any cascade).
- **R4 (one volunteer = one school)** is enforced at the slot-class create step. If the picked volunteer has an active `school_volunteer` row at a different school, the create call is blocked with: "This volunteer is already at school X. Remove them from there first."

**4. CHO scope is computed from `partner_worknode` mapping (not `school_volunteer`).** CHO users see schools where their `worknode_id` maps to a `partner_worknode` row with a valid `partner_id`. This decouples CHO access from slot-class participation — a CHO whose Worknode tagging is in place has Session-Ops access immediately, regardless of whether they've been picked into any slot-class yet. The check has two failure conditions: (a) user has no `worknode_id`, or (b) user has a `worknode_id` but no `partner_worknode` row matches with a valid `partner_id`. In either case, CHO sees an empty schools list with the message: "You are not assigned to any schools or partner. Please contact your community organizer or admin."

**5. CHO has full CRUD permissions on their scoped schools.** CHO is not read-only. Within the schools their Worknode mapping resolves to, CHO can create/edit/delete classes, sections, children, slots, slot-classes (and calendar items in future milestones). The only thing scoping CHO is _which schools they see_; what they can _do_ inside those schools matches CO permissions. The `can_user_modify_school` helper allows CHO when the school is in their worknode-derived scope.

**6. Slots are pure weekly patterns, no per-date materialization.** A slot says "Monday 11-12 AM" — applies to every Monday in the academic year. Per-date awareness arrives in M4 via the calendar/holiday layer.

**7. Five-table slot-class composition.** When a CO assigns a section + subject + volunteer(s) to a slot, multiple table inserts happen in a single transaction:
- `class_section_subject`
- `child_subject` (one row per active child in the section)
- `slot_class_section`
- `slot_class_section_volunteer` (1-2 rows for vol1/vol2)
- `school_volunteer` (one row per volunteer, **only if they don't already have an active row at this school**)

**8. `child_subject` is history-only.** Not used for current-state queries. Always present a child's current subjects by joining child → child_class_section → class_section → class_section_subject. The `child_subject` table exists for parity with the existing Bubble system and for future reporting use. M3 adds rows in two flows: (a) slot-class creation creates rows for all currently-active children in the section, (b) M2's child enrollment service is extended to also create rows for the new child if their target section already has class_section_subject rows.

**9. Three-state lifecycle continues from M2.** Every M3 table has `is_active`, `removed`, `deleted_at` (except Subject and PartnerWorknode — read-only/seeded catalogs).

| `is_active` | `removed` | Meaning |
|---|---|---|
| true | false | Active |
| false | false | Inactive (data preserved, business rules ignore) |
| false | true | Soft-deleted (treated as deleted by app) |
| true | true | Not possible |

**10. Subject is a universal catalog.** Like Class — seeded once, never deactivated. Schema is minimal: `subject_id`, `subject_name`, `program_id`. No `is_active`/`removed`. Seeded rows: "Foundation Day 1" and "Foundation Day 2" under Foundation Program.

**11. `partner_worknode` is a synced mapping table, read-only in Session-Ops.** Comes from the same Hasura sync. Session-Ops never writes to it. It's purely a lookup table to translate Session-Ops `partner_id` → Worknode `worknode_id` → list of users tagged with that `worknode_id`. Schema has 12 columns but M3 only uses `partner_id` and `worknode_id`; the other 10 columns are stored for future features.

**12. School identifier convention continues from M2.** All M3 tables that reference a school use `school_id` (FK to `partner.partner_id`, db_constraint=False).

**13. Deletion cascade flows are explicit, not via Django CASCADE.** R9 prohibits CASCADE. All cascades are explicit in service code, soft-deleting child rows in the same transaction.

**14. Schedule view in M3 is a detail view per school, not a calendar.** Layout is slot-by-slot showing all info. Calendar-style monthly view is M4+.

**15. Section delete is blocked if active slot-classes reference it.** Extends M2's section delete rule (which already blocks if children are active). This means before deleting a section, CO must first remove any slot_class_section rows that point to it. Lives as a small M2 service extension applied during M3 build (same pattern as the `enroll_child` extension for `ChildSubject`).

**16. Slot delete is blocked if active slot-classes exist.** No surprise cascades on slot delete. If the slot has any `slot_class_section` rows with `is_active=True, removed=False`, the delete call returns an error: "Cannot delete this slot. Remove the {N} class assignments first." CO must explicitly tear down slot-classes one by one. Inactive-but-not-removed rows (`is_active=False, removed=False`) do not block — only active rows do. Slot edit (name, day, times) is not blocked, even with active slot-classes — overlap check still applies.

## F-M3-3 — Volunteer auto-population (Worknode matching)

### What it does

- CO opens the Volunteers tab on a school
- Frontend calls `GET /api/schools/{school_id}/volunteers/`
- Backend resolves `partner_worknode` for the school → gets `worknode_id`
- Backend queries `User` where `worknode_id == that_worknode_id`, `is_active=True, removed=False`
- Returns the list of matching users
- Frontend renders volunteer cards (name, role, active slot-class count if any)
- No actions on the tab (read-only)

Empty states:
- If school has no `partner_worknode` row: "No Worknode found for this school. Please contact admin."
- If `partner_worknode` exists but no users match: "No volunteers found for this school. Please make sure you've tagged the Worknode in user management."

### Backend — service

#### `services/volunteers/list.py`

`list_school_volunteers(school_id, requesting_user) -> dict`

```python
def list_school_volunteers(school_id, requesting_user):
    if not can_user_view_school(requesting_user, school_id):
        raise PermissionDenied()

    worknode_ids = PartnerWorknode.objects.filter(
        partner_id=str(school_id),
    ).values_list("worknode_id", flat=True).distinct()

    if not worknode_ids:
        return {
            "status": "no_worknode",
            "message": "No Worknode found for this school. Please contact admin.",
            "volunteers": [],
        }

    volunteers = User.objects.filter(
        worknode_id__in=list(worknode_ids),
        is_active=True,
        removed=False,
    ).order_by("user_name")

    if not volunteers.exists():
        return {
            "status": "no_volunteers",
            "message": "No volunteers found for this school. Please make sure you've tagged the Worknode in user management.",
            "volunteers": [],
        }

    serialized = []
    for v in volunteers:
        active_slot_class_count = SlotClassSectionVolunteer.objects.filter(
            volunteer_id=v,
            is_active=True,
            removed=False,
            slot_class_section_id__slot_id__school_id=school_id,
        ).count()
        serialized.append({
            "user_id": v.user_id,
            "user_name": v.user_name,
            "user_role": v.user_role,
            "active_slot_class_count": active_slot_class_count,
        })

    return {"status": "ok", "volunteers": serialized}
```

## F-M3-4 — CHO scope activation

### What it does

CHO scope, which has been empty since M1, becomes real. CHO users log in and see schools where their `worknode_id` maps to a `partner_worknode` row with a valid `partner_id`. The scope is independent of `school_volunteer` — a CHO with valid Worknode tagging has access immediately, regardless of any slot-class participation.

Within their scoped schools, CHO has full CRUD permissions on classes, sections, children, slots, and slot-classes — the same write permissions as a CO, just on a different set of schools.

If a CHO has no `worknode_id`, or has a `worknode_id` but no matching `partner_worknode` row with a valid `partner_id`, they see an empty schools list and the message: **"You are not assigned to any schools or partner. Please contact your community organizer or admin."**

### Backend — services

#### `services/rbac/scope.py` (EXTEND)

```python
def schools_visible_to(user):
    if user.is_admin:
        return Partner.objects.filter(is_active=True, removed=False)

    if user.has_co_role or user.has_cxo_role:
        return Partner.objects.filter(
            co_id=user.user_id, is_active=True, removed=False
        )

    # CHO via partner_worknode mapping
    if user.has_cho_role:
        if user.worknode_id is None:
            return Partner.objects.none()
        partner_ids = PartnerWorknode.objects.filter(
            worknode_id=user.worknode_id,
        ).exclude(
            partner_id__isnull=True,
        ).exclude(
            partner_id="",
        ).values_list("partner_id", flat=True).distinct()
        if not partner_ids:
            return Partner.objects.none()
        return Partner.objects.filter(
            partner_id__in=list(partner_ids),
            is_active=True, removed=False,
        )

    return Partner.objects.none()


def can_user_view_school(user, school_id):
    return schools_visible_to(user).filter(partner_id=school_id).exists()


def can_user_modify_school(user, school_id):
    """CHO has the same CRUD access as CO, but only within their worknode-scoped schools."""
    if user.is_admin:
        return Partner.objects.filter(
            partner_id=school_id, is_active=True, removed=False
        ).exists()
    if user.has_co_role or user.has_cxo_role:
        return Partner.objects.filter(
            partner_id=school_id, co_id=user.user_id,
            is_active=True, removed=False
        ).exists()
    if user.has_cho_role:
        return schools_visible_to(user).filter(partner_id=school_id).exists()
    return False
```

Hybrid role note: M1 RBAC assumes single role per user. Users with a "CO + CHO" hybrid role are not allowed to log in (restricted upstream). M3 does not need to handle role union.

```python
        raise PermissionDenied()

        raise ValidationError("start_time must be before end_time")
```

## F-M3-6 — Slot edit and delete

### What it does

- CO can edit a slot's name, day, start/end times (R7 overlap re-checked on time/day changes)
- Edit is allowed even when the slot has active slot_class_section rows
- CO can soft-delete a slot **only if it has no active slot_class_section rows**

- Inactive-but-not-removed slot_class_section rows (`is_active=False, removed=False`) do not block delete

```python
@transaction.atomic
def soft_delete_slot(slot_id, user):
    slot = Slot.objects.select_for_update().get(slot_id=slot_id, removed=False)

    if not can_user_modify_school(user, slot.school_id):
        raise PermissionDenied()

    # Block delete if active slot-classes exist
    active_slot_class_count = SlotClassSection.objects.filter(
        slot_id=slot,
        is_active=True,
        removed=False,
    ).count()

    if active_slot_class_count > 0:
        raise ConflictError(
            f"Cannot delete this slot. Remove the {active_slot_class_count} class "
            f"assignment{'s' if active_slot_class_count != 1 else ''} first."
        )

    now = timezone.now()
    slot.is_active = False
    slot.removed = True
    slot.deleted_at = now
    slot.updated_by = user
    slot.save()

    return slot
```

```python
@transaction.atomic
def create_slot_class(slot_id, payload, user):
    slot = Slot.objects.select_for_update().get(slot_id=slot_id, removed=False)

    if not can_user_modify_school(user, slot.school_id):
        raise PermissionDenied()

    section_id = payload["class_section_id"]
    subject_id = payload["subject_id"]
    volunteer_1_id = payload["volunteer_1_id"]
    volunteer_2_id = payload.get("volunteer_2_id")

    # R3
    if volunteer_2_id and volunteer_1_id == volunteer_2_id:
        raise ValidationError("Vol1 and Vol2 cannot be the same volunteer")

    section = ClassSection.objects.get(class_section_id=section_id, removed=False)
    if section.school_id != slot.school_id:
        raise ValidationError("Section does not belong to this school")

    # R5
    existing = SlotClassSection.objects.filter(
        slot_id=slot, class_section_id=section,
        is_active=True, removed=False,
    ).exists()
    if existing:
        raise ConflictError(f"Section {section.section_name} is already scheduled in this slot")

    # R6
    volunteers_in_slot = SlotClassSectionVolunteer.objects.filter(
        slot_class_section_id__slot_id=slot,
        is_active=True, removed=False,
    ).values_list("volunteer_id", flat=True)

    if volunteer_1_id in volunteers_in_slot:
        raise ConflictError("Vol1 is already teaching another section in this slot")
    if volunteer_2_id and volunteer_2_id in volunteers_in_slot:
        raise ConflictError("Vol2 is already teaching another section in this slot")

    # Validate worknode match
    _validate_volunteer_worknode_match(slot.school_id, volunteer_1_id)
    if volunteer_2_id:
        _validate_volunteer_worknode_match(slot.school_id, volunteer_2_id)

    # R4: each volunteer must not have active school_volunteer at a DIFFERENT school
    for vid in [volunteer_1_id, volunteer_2_id]:
        if vid is None:
            continue
        other_school_sv = SchoolVolunteer.objects.filter(
            volunteer_id_id=vid,
            is_active=True, removed=False,
        ).exclude(school_id=slot.school_id).first()
        if other_school_sv:
            vol = User.objects.get(user_id=vid)
            other_school = Partner.objects.get(partner_id=other_school_sv.school_id)
            raise ConflictError(
                f"{vol.user_name} is already at school '{other_school.partner_name}'. "
                f"Remove them from there first."
            )

    say = get_or_create_school_academic_year(slot.school_id, user)

    # Step 1: class_section_subject
    css = ClassSectionSubject.objects.create(
        class_section_id=section,
        subject_id_id=subject_id,
        created_by=user,
    )

    # Step 2: child_subject for all active children
    active_children = Child.objects.filter(
        child_id__in=ChildClassSection.objects.filter(
            class_section_id=section,
            is_active=True, removed=False,
        ).values("child_id"),
        is_active=True,
    )

    ChildSubject.objects.bulk_create([
        ChildSubject(
            child_id=child,
            class_section_subject_id=css,
            created_by=user,
        )
        for child in active_children
    ])

    # Step 3: slot_class_section
    scs = SlotClassSection.objects.create(
        slot_id=slot,
        class_section_id=section,
        class_section_subject_id=css,
        created_by=user,
    )

    # Step 4: slot_class_section_volunteer (1-2 rows)
    SlotClassSectionVolunteer.objects.create(
        slot_class_section_id=scs,
        volunteer_id_id=volunteer_1_id,
        created_by=user,
    )
    if volunteer_2_id:
        SlotClassSectionVolunteer.objects.create(
            slot_class_section_id=scs,
            volunteer_id_id=volunteer_2_id,
            created_by=user,
        )

    # Step 5: ensure school_volunteer for each
    for vid in [volunteer_1_id, volunteer_2_id]:
        if vid is None:
            continue
        existing_sv = SchoolVolunteer.objects.filter(
            school_id=slot.school_id,
            volunteer_id_id=vid,
            is_active=True, removed=False,
        ).first()
        if not existing_sv:
            SchoolVolunteer.objects.create(
                school_id=slot.school_id,
                volunteer_id_id=vid,
                school_academic_year_id=say,
                created_by=user,
            )

    return scs


def _validate_volunteer_worknode_match(school_id, volunteer_id):
    """Volunteer must be discoverable via the school's worknode mapping."""
    worknode_ids = PartnerWorknode.objects.filter(
        partner_id=str(school_id),
    ).values_list("worknode_id", flat=True)

    if not worknode_ids:
        raise ValidationError(
            "This school has no Worknode mapping. Volunteer cannot be assigned."
        )

    user_matches = User.objects.filter(
        user_id=volunteer_id,
        worknode_id__in=list(worknode_ids),
        is_active=True, removed=False,
    ).exists()

    if not user_matches:
        raise ValidationError(
            "This volunteer is not in the Worknode-tagged list for this school."
        )
```

### Edit slot-class

`edit_slot_class(scs_id, payload, user)` handles three sub-flows:

1. **Edit volunteer 1 or 2 only:**

2. **Edit section:** Full cascade reset.

3. **Edit subject:** Full cascade reset.

```python
    if not can_user_modify_school(user, slot.school_id):
        raise PermissionDenied()

    now = timezone.now()

    affected_volunteer_ids = set(
        SlotClassSectionVolunteer.objects.filter(
            slot_class_section_id=scs, is_active=True, removed=False
        ).values_list("volunteer_id", flat=True)
    )

    SlotClassSectionVolunteer.objects.filter(
        slot_class_section_id=scs, is_active=True, removed=False
    ).update(is_active=False, removed=True, deleted_at=now, updated_by=user)

    ClassSectionSubject.objects.filter(
        class_section_subject_id=scs.class_section_subject_id,
        is_active=True, removed=False,
    ).update(is_active=False, removed=True, deleted_at=now, updated_by=user)

    scs.is_active = False
    scs.removed = True
    scs.deleted_at = now
    scs.updated_by = user
    scs.save()

    _reconcile_school_volunteer_for_volunteers(
        slot.school_id, affected_volunteer_ids, user
    )


def _reconcile_school_volunteer_for_volunteers(school_id, volunteer_ids, user):
    """For each volunteer, if they have no remaining active slot_class_section_volunteer
    rows at this school, soft-delete their school_volunteer row."""
    if not volunteer_ids:
        return
    now = timezone.now()
    for vid in volunteer_ids:
        has_remaining = SlotClassSectionVolunteer.objects.filter(
            volunteer_id_id=vid,
            is_active=True, removed=False,
            slot_class_section_id__slot_id__school_id=school_id,
        ).exists()
        if not has_remaining:
            SchoolVolunteer.objects.filter(
                school_id=school_id,
                volunteer_id_id=vid,
                is_active=True, removed=False,
            ).update(
                is_active=False, removed=True, deleted_at=now, updated_by=user
            )
```

This reconciliation helper is reused by:
- F-M3-7 slot-class delete (above)
- F-M3-7 slot-class volunteer swap (edit flow)

# Part 3 — Wrap-up

## Resolved decisions (answers captured at M3 spec time)

- **`worknode_id` and `partner_worknode` in Hasura.** Confirmed they will be exposed by the same Hasura sync API. To be verified against the actual API surface before Day 1.
- **`partner_worknode` cardinality: one-to-one.** Each partner maps to a single worknode_id. Sync upsert key is `partner_id`. The 12 columns include other mapping metadata (city_name, state, etc.) but the relationship is 1:1.
- **Hybrid roles not allowed.** Login is restricted to single-role users — a "CO Full Time + CHO" hybrid cannot log in. M3 RBAC assumes single role.
- **Section delete blocked if active slot-classes reference it.** M2's section delete service is extended in M3 to add this check, analogous to the existing "active children" block. Lives in `services/sections/delete.py`.
- **Subject duplication across slots is acceptable.** M3 creates a new `class_section_subject` per slot-class. Multiple slot-classes for "section 5-A teaching Foundation Day 1" at different times each get their own `class_section_subject` row. Not an error; not refactored.
- **Volunteer 1 and 2 are equivalent.** No role column on `slot_class_section_volunteer`. Both stored as separate rows, both treated the same.

## Deferred to later milestones

- **Worknode reassignment mid-academic-year.** If sync changes a volunteer's `worknode_id`, they'll disappear from the old school's auto-list and appear in the new one — but their existing `slot_class_section_volunteer` rows at the old school remain active. Session-Ops does not auto-cleanup based on sync changes in M3. Handling this case (admin alert, cleanup workflow) is deferred to M5. **Documented behavior for M3:** old school's CO sees the volunteer in active slot-classes but not in the auto-populated volunteer list; CO must manually edit/delete those slot-classes if needed.
