# Part 1 — Milestone Overview

## Production goal

At the end of M7, all live operational data from the Bubble session-ops app has been migrated into the new Session-Ops Postgres database. Every school, class, section (bucket), child, slot-class, volunteer assignment, session, and holiday that CO/CHO/admin have in Bubble today is faithfully represented in Session-Ops. The tool is ready for a formal cutover from Bubble.

The migration is **built as a re-runnable pipeline**, not a one-shot script. Every table has its own dedicated migration workflow. Each workflow can be run independently, wiped and reloaded, and validated in isolation. This lets us iterate on migration logic against real data over the transition period without irreversible consequences. The final cutover is just one more run of the same pipeline — no special-case code path.

The migration reuses the exact architectural pattern from M8a: **Hasura exposes shape-fitted data as REST APIs, and n8n workflows pull from Hasura and POST to Session-Ops.** No new infrastructure needs to be built — the pipeline plumbing is already running. What's new is (a) the 20 dbt models that transform Bubble data into Session-Ops shape, (b) 20 loader endpoints on Session-Ops that accept the transformed rows, and (c) 20 n8n workflows that orchestrate the load.

## What does NOT ship in M7

Hard out-of-scope. Don't build any of these in M7 even if asked.

- **Post-migration data flow from Session-Ops to warehouse.** Once Session-Ops takes over as the source of truth, a new pipeline needs to pump Session-Ops Postgres → data warehouse → dbt → Dots. That's the data platform team's work, not ours. M7 delivers a migrated Session-Ops DB; wiring it back to the warehouse is out of scope.
- **User migration.** Users (CO, CHO, admin, volunteers) are already synced by M8a (realtime) + M4 (incremental cron). M7 does not touch the `user` table.
- **Partner migration.** Partners are already synced by M1 + M4 upstream infrastructure. M7 does not touch the `partner` table.
- **`partner_worknode` migration.** Already has its own dedicated sync (`sessionops/management/commands/sync_partner_worknode.py` → `run_partner_worknode_sync`), same operational pattern as `partner`/`user`. M7 does not touch it — it's an external dependency the same way `partner` and `user` are (decision #9 below).
- **Incremental sync from Bubble during transition period.** M7 uses periodic full-refresh (Model 4). Every run wipes the destination and reloads. No CDC, no streaming, no diff-based sync.
- **Bubble decommissioning.** Turning Bubble off is a separate step handled after cutover confidence. M7 delivers the migration; Bubble retirement is a subsequent decision.
- **Session-Ops → Bubble backward sync.** One-way only. Data flows Bubble → Session-Ops during M7. Nothing flows back.
- **Historical data reconciliation.** If Bubble has data quality issues (orphaned FKs, empty strings, duplicate active rows), M7's migration mode logs and skips them but does not attempt to auto-repair Bubble's history.
- **A UI dashboard for migration progress.** Progress is visible through n8n's execution UI + n8n data tables. No dedicated Session-Ops admin screen.
- **Multi-tenant migration.** Assumes a single Bubble instance and a single Session-Ops destination. Not designed to support parallel migrations across multiple MAD tenants.
- **Rollback of individual rows post-migration.** If a specific migrated row turns out to be wrong, the fix is either (a) rerun the migration for that table, or (b) fix directly in Session-Ops. No per-row rollback tooling.

> If something here turns out to be unexpectedly needed for M7, talk to the human first before adding scope.

## Key architectural decisions for M7

**1. Model 4 — periodic full-refresh migration.** Each migration workflow wipes the target Session-Ops table (or upserts by PK, which effectively achieves the same result) and reloads from the freshest Bubble data. No CDC. No incremental diffs. Re-runnable as often as we want during the transition period. Final cutover is just one more run.

**2. Bubble's custom integer PKs become Session-Ops PKs unchanged.** Bubble already has a custom `child_id`, `school_class_id`, `class_section_id`, etc. integer column on every table (maintained by Bubble workflows on CRUD). These integers are unique per table in Bubble. Session-Ops uses them directly as its PKs. No source_ref column needed; no mapping table needed. Upsert works because same PK on both sides identifies the same logical row.

**3. Same architecture as M8a — Hasura + n8n.** Bubble → warehouse (existing Dalgo pipeline) → dbt (build for M7) → Hasura (existing) → n8n → Session-Ops loader endpoints. No new orchestration infrastructure. Same operational patterns for retry, dead-letter, logging.

**4. dbt does the transformation heavy-lifting.** All data cleaning (empty-string to null, type coercion, joins, denormalization, filtering) happens in dbt models. Hasura exposes the already-clean output. n8n is a simple pump — fetch from Hasura, POST to Session-Ops, log the result. No transformation logic in n8n.

**5. Migration-mode validation suppression.** Session-Ops loader endpoints run with a "migration mode" flag (activated by service-token auth). Under migration mode, business rules that assume user-driven writes are suppressed — R1 (max 5 children per bucket), R-class (one active child_class per child), R-bucket (volunteers ≤ children), R2 (1-5 volunteers), R4 (one volunteer per school), R6 (volunteer not in two slot-classes in same slot). Bubble may have data that violates these; we accept it, log it, and reconcile manually later if needed. User-driven writes after cutover enforce all rules normally.

**6. One n8n workflow per table.** 20 workflows total. Each workflow is independent, testable, and re-runnable. This gives maximum isolation for the first migration attempts. Once patterns are proven across the first 5-6 tables, later workflows can be built quickly by copying the template.

**7. Sync semantics: 2xx = success, 4xx = log-and-skip-row, 5xx = stop-workflow.** Individual bad rows don't block the migration. Server errors stop the workflow so we can investigate before continuing. Every row's outcome is logged in an n8n data table (`migration_log`) for post-run audit.

**8. Bulk load order follows FK dependency graph.** Layer 0 (reference data) → Layer 1 (school-scoped structural) → Layer 2 (children + assignments) → Layer 3 (slots + scheduling). Never load a child before its parent. This is enforced by workflow execution order, not by DB constraints (constraints are what we're trying to satisfy).

**9. `partner`, `user`, and `partner_worknode` are NOT migrated.** All three are already synced by existing infrastructure (`partner`/`user` via M1+M4 cron and M8a realtime; `partner_worknode` via its own `sync_partner_worknode` management command). M7 assumes all three are populated before M7 workflows run. If any is empty or stale, migration will fail with FK violations — that's an operational precondition, not a bug.

**10. Audit log lives in n8n data tables, not in Session-Ops.** No new `migration_log` table on the Session-Ops schema. Every row's migration attempt is logged in an n8n data table (analogous to `webhook_request_log` from M8a). Retention: keep for 2-3 months after cutover for audit, then delete. Session-Ops schema stays clean.

**11. Cutover is a scheduled event, not a big-bang emergency.** Given the data volume (~50-80k rows total across all tables, full migration in 30-60 minutes), cutover doesn't require a maintenance weekend. It's a coordinated event: Bubble goes read-only, final migration runs, Session-Ops opens for users. 1-2 hour window is sufficient.

**12. Rollback window: Bubble stays read-only for 1-2 weeks after cutover.** If cutover reveals catastrophic issues in Session-Ops that we can't fix quickly, users can be pointed back at Bubble (in read-only mode) as a fallback. After 1-2 weeks of confidence, Bubble is officially retired.

**13. `school_academic_year` replaces the phantom `worknode` table in Layer 0.** Two corrections to the original draft:
  - `SchoolAcademicYear` (`sessionops/models/academic_year.py`) is a hard FK dependency for `school_class`, `slot` (required FK), `school_volunteer` (optional FK), `school_session_details`, and `batch_child` — none of these can load correctly without it. It was missing from the original plan entirely. It has no dependency on `partner` or `user` (just a raw `school_id` int + a FK to `academic_year`), so it belongs in Layer 0 — but **within Layer 0, `academic_year` must load before `school_academic_year`** (the one exception to "Layer 0 workflows run in parallel"). The master orchestration workflow (F-M7-6) sequences these two specifically; `program`, `subject`, and `class` remain fully parallel with `academic_year`.
  - There is no standalone `worknode` table in Session-Ops. `worknode_id` is only ever a raw integer referenced by `PartnerWorknode.worknode_id` and `User.worknode_id` — confirmed, not an open question. The original draft's Layer 0 entry for "worknode" is dropped.
  - `partner_worknode` is dropped from Layer 1 per decision #9 (already synced separately) — it is not one of the 20 tables. Neither is `subject` — see decision #18.

**14. All historical rows migrate, not just active ones.** Confirmed decision (was an open question in the original draft): tables with history — `child_class`, `child_class_section`, `batch_child`, `child_program`, `school_volunteer` — migrate every row including soft-deleted/inactive ones. This preserves attrition/audit history and gives M8a's realtime sync a complete picture of prior state. `is_active`/`removed` flags carry over as-is from Bubble's equivalent state.

**15. `school_id`-style references are validated at the service layer, not the DB.** Following the same pattern as `Partner.co_id` (D024): `child.school_id`, `class_section.school_id`, `slot.school_id`, `school_holiday.school_id`, `batch_child.school_id`, and `school_academic_year.school_id` are all plain integer columns, not DB-level foreign keys to `partner`. The loader endpoints must explicitly validate these against `Partner.objects.filter(partner_id=...)` in Python — an invalid `school_id` will NOT raise an `IntegrityError`, it will silently insert. Treat this the same as a required FK for orphan-detection purposes (422 `orphan_fk` on failure), even though there's no DB constraint backing it up.

**16. `class_section`'s bucket-slug fields are computed by dbt, not the loader.** Per M6, `class_section.section_name` is a normalized slug and `section_display_name` holds the original text (e.g. `"Care Monster"` → slug `"care_monster"`). The `m7_migration_class_section` dbt model applies the same normalization rule as `services/sections/slug.py::normalize_section_slug` (lowercase, strip, non-alphanumeric runs → single underscore) to Bubble's bucket name, producing both columns before the row reaches Hasura. This keeps the loader endpoint dumb, consistent with decision #4. `school_class_id` and `section_code` are optional post-M6 — dbt passes through Bubble's legacy class link if the bucket has one, else null.

**17. `slot_class_section_volunteer` is one row per volunteer, not vol1/vol2 columns.** The Session-Ops model has no `vol1_id`/`vol2_id` split — each assigned volunteer is a separate row (1-5 rows per slot-class post-M6). If Bubble's source table stores volunteers as vol1/vol2 columns, the `m7_migration_slot_class_section_volunteer` dbt model must unpivot into one output row per non-null volunteer.

**18. `subject` is not migrated — confirmed 2026-07-15.** `subject` has ~2-3 rows total and M6's migration `0027_m6_seed_foundation_subject` already idempotently seeds a fixed `Subject` row (`subject_name="Foundation"`). No dedicated loader endpoint, dbt model, or n8n workflow for it. `class_section_subject`'s `subject_id` FK resolves against whatever `Subject` rows already exist in Session-Ops — same shape as `partner`/`user`/`partner_worknode` being external preconditions rather than migration targets, just for a much smaller table. If Bubble turns out to have subject variants beyond what M6 seeded, add them manually rather than building a migration workflow for a 2-3-row table.

**19. `child_removal_log` was missing from every earlier draft — added, Layer 2.** Found during a full model audit (2026-07-15): `ChildRemovalLog` (`sessionops/models/child.py`) is one row per child-removal event — `child_id` (real FK to `Child`), `co_id` (raw integer, loose reference to `User.user_id` — the model's own comment calls it a "loose FK", so treat as a warn-only check, not a hard `orphan_fk` skip, per decision #15's spirit but not its letter), `school_id` (raw integer, decision #15 applies normally), `removed_reason`, `other_details`, `removed_datetime`. This is exactly the attrition-history data BUSINESS_RULES.md's R10 exists for, and per decision #14 (migrate all historical rows) it belongs in the migration. Depends only on `Child` (Layer 2), so it loads alongside `child_class`/`child_class_section`. Unlike every other table here, it has **no `created_by`/`updated_by` fields** — the "migration bot" system-user question (see the F-M7-1 implementation plan's Open Questions) doesn't apply to it.

**Net table count: 20** (program, academic_year, class, school_academic_year, school_class, school_volunteer, school_session_details, school_holiday, class_section, child, child_class, child_class_section, child_removal_log, class_section_subject, child_subject, batch_child, child_program, slot, slot_class_section, slot_class_section_volunteer) — not 21 (the original draft), 22 (an interim correction), or 19 (before `child_removal_log` was found). A full audit of all 28 model classes in `sessionops/models/` confirmed no further gaps: `password_reset_tokens`, `realtime_sync_log`, `sync_run`, and `user_auth` are all Session-Ops-internal tables with no Bubble source, correctly excluded.

### Request body

Single row of Bubble-shaped data, JSON, all keys matching the Session-Ops column names exactly. The full body specs per table live in `M7-Table-Specs.xlsx` (companion doc).

Every body includes the primary key column (`child_id`, `school_class_id`, etc.) as the first field. This PK is the upsert key.

### Auth

Header: `Authorization: Bearer <migration_service_token>`

The migration service token is a separate credential from the M8a service token. Reason: different validation semantics (M8a enforces business rules; migration suppresses them). Auth middleware checks the token and sets `request.auth = {'mode': 'migration'}` on the request; the loader endpoint dispatches on `request.auth['mode']` to apply migration-mode semantics.

Token generation and rotation: same operational pattern as M8a. Store in Django settings + Hasura environment. Rotate on cutover completion.

### Service layer pattern

Each table gets a service function following this pattern:

```python
# sessionops/services/migration/migrate_child.py
from django.db import transaction
from sessionops.models import Child, SchoolClass, ClassSection, Partner

def migrate_child_row(payload: dict, user: User) -> tuple[str, list[str]]:
    """
    Upsert a single child row from Bubble data.
    Returns: (status, warnings)
    """
    child_id = payload["child_id"]
    warnings = []

    # school_id is NOT a DB-level FK (BigIntegerField only, per D024 pattern) —
    # validate against Partner explicitly since Postgres won't catch a bad reference.
    if not Partner.objects.filter(partner_id=payload["school_id"]).exists():
        raise MigrationValidationError(
            "orphan_fk",
            f"school_id {payload['school_id']} does not exist in partner"
        )

    # Validate parent FKs exist
    if not SchoolClass.objects.filter(school_class_id=payload["school_class_id"]).exists():
        raise MigrationValidationError(
            "orphan_fk",
            f"school_class_id {payload['school_class_id']} does not exist"
        )
    if payload.get("class_section_id") and not ClassSection.objects.filter(
        class_section_id=payload["class_section_id"]
    ).exists():
        warnings.append(f"class_section_id {payload['class_section_id']} does not exist; setting to NULL")
        payload["class_section_id"] = None

    with transaction.atomic():
        existing = Child.objects.filter(child_id=child_id).first()
        if existing:
            # Update
            changes = []
            for field, new_val in payload.items():
                if getattr(existing, field, None) != new_val:
                    setattr(existing, field, new_val)
                    changes.append(field)
            existing.save()
            return ("updated", warnings)
        else:
            # Insert
            Child.objects.create(**payload)
            return ("inserted", warnings)
```

Key details:
- **Explicit PK insert.** Django is instructed to use the provided integer PK, not auto-generate. This is done by setting the PK field explicitly on `create()`.
- **`school_id`-style fields need explicit service-layer FK validation.** Per decision #15, these are raw `BigIntegerField` columns with no DB constraint — Postgres will happily insert a `school_id` that doesn't exist in `partner`. Every loader function that writes one of these columns must check it against `Partner` explicitly and treat a miss as `orphan_fk`, same as a real FK.
- **Warn-then-null on orphan optional FKs.** If a Bubble child references a non-existent optional FK (like `class_section_id`), we log a warning and set the FK to null rather than fail the row.
- **Fail on orphan required FKs.** If a Bubble child references a non-existent required FK (like `school_class_id`), we return 422 with reason=`orphan_fk`. Row is skipped.
- **Transaction per row.** Each row is its own transaction. Failures don't roll back previously-migrated rows.

### FK integrity handling

For each table, the loader validates all FK columns — both real DB FKs and `school_id`-style raw-integer references (decision #15) — against Session-Ops's current state. Two failure modes:

- **Required FK missing** → 422 with `reason=orphan_fk`. Row is skipped. n8n logs and continues.
- **Optional FK missing** → set to null, add warning to response. Row is inserted/updated.

This means load order matters: parent tables must be migrated before child tables. The n8n workflow orchestration enforces this by running workflows in Layer 0 → 1 → 2 → 3 order, with `academic_year` before `school_academic_year` inside Layer 0 (decision #13).

### Explicit PK preservation

Django's default behavior is to auto-generate PKs on `INSERT`. We need to override this to accept explicit PKs from Bubble. Two options:

- **Option A:** Set the PK field explicitly and call `save()`. Works but bypasses Django's `.create()` shortcuts.
- **Option B:** Use `bulk_create()` with `ignore_conflicts=False` — Django preserves explicit PKs.
- **Option C:** Use raw SQL `INSERT ... ON CONFLICT (pk) DO UPDATE`. Fastest, most explicit, no ORM overhead.

**Decision: Option A for simplicity + explicit ORM audit trail.** Performance is not a concern at 50-80k total rows. Each loader function sets the PK explicitly on the model instance and calls `save()`.

**Post-migration housekeeping:** Postgres sequences (used by `serial` PKs) must be advanced to `max(pk) + 1` after all migrations complete, so that user-driven writes don't collide with migrated PKs. A one-time SQL script runs post-cutover (full script in Part 3).

## F-M7-2 — Migration mode validation suppression

**Goal:** When a request comes in with the migration service token, suppress business-rule checks that assume user-driven writes.

### Rules suppressed under migration mode

| Rule | Normal enforcement | Migration mode |
|------|-------------------|----------------|
| R1: Max 5 children per bucket | Enforced | Logged as warning, not blocked |
| R2: 1-5 volunteers per slot-class | Enforced | Logged as warning, not blocked |
| R3: Volunteer uniqueness in slot-class | Enforced | Logged as warning, not blocked |
| R4: One volunteer = one school | Enforced by M8a | Logged as warning, not blocked |
| R5: Same bucket not twice in same slot | Enforced | Logged as warning, not blocked |
| R6: Volunteer not in two slot-classes in same slot | Enforced | Logged as warning, not blocked |
| R7: No overlapping slots same school same day | Enforced | Logged as warning, not blocked |
| R-bucket: count(vols) ≤ count(children) | Enforced | Logged as warning, not blocked |
| R-class: One active child_class per child | Enforced at service layer | Logged as warning, not blocked |
| R-bucket-membership: One active bucket per child | Enforced | Logged as warning, not blocked |
| R-section-slug: Slug unique per school | Enforced by DB unique index | **Cannot suppress** — DB will reject |
| NOT NULL constraints | Enforced by DB | **Cannot suppress** — DB will reject |
| FK constraints (real DB FKs) | Enforced by DB | Row skipped as `orphan_fk` |
| `school_id`-style raw-int references (decision #15) | No DB enforcement — service layer only | Same service-layer check runs in migration mode; skipped as `orphan_fk` on failure, not silently inserted |

**Rules that CAN'T be suppressed:** DB-level constraints (NOT NULL, unique indexes, real FK constraints). Any Bubble row that violates these will get rejected. The loader endpoint returns 422 with `reason=constraint_violation` and the row is skipped.

**Rules that CAN be suppressed:** Application-layer business rules enforced in service functions. Migration-mode dispatch skips the check but records a warning. Note: the `school_id`-style orphan check (decision #15) is NOT a business rule to suppress — it's a data-integrity check that runs in both modes, since there's no DB backstop for it.

### Implementation

Each service function is refactored to accept an `enforcement_mode` parameter:

```python
def enroll_child(payload, user, enforcement_mode='user'):
    if enforcement_mode == 'user':
        # Check R1: bucket capacity
        # Check R-class: one active child_class
        # etc.
    elif enforcement_mode == 'migration':
        # Skip R1, R-class, etc.
        # Log warnings if invariants would be violated
    ...
```

The loader endpoint calls the service function with `enforcement_mode='migration'`. Regular user-driven endpoints call with `enforcement_mode='user'` (default).

**Alternative approach considered:** Separate migration-only service functions duplicating the enrollment logic without checks. Rejected because it doubles the surface area to test.

## F-M7-3 — dbt migration models

**Goal:** 20 dbt models that read from your existing warehouse (Bubble → Dalgo → warehouse) and produce output tables shaped exactly like Session-Ops's schema.

**Ownership:** You build these. The M7 plan documents the required output shape for each model in `M7-Table-Specs.xlsx`. The plan does not prescribe the source-side warehouse tables (that depends on your existing dbt structure).

### Model naming convention

```
m7_migration_{session_ops_table_name}.sql
```

Examples:
- `m7_migration_child.sql`
- `m7_migration_school_class.sql`
- `m7_migration_class_section.sql`
- `m7_migration_school_academic_year.sql`

### Output requirements

Each dbt model produces:
- Column names matching Session-Ops schema exactly (`child_id`, not `id` or `pk`)
- Types compatible with Session-Ops Postgres types
- All required columns present, even if null
- Empty strings coerced to null
- Boolean strings ('true', 'false', 'yes', 'no') coerced to bool
- Dates in ISO 8601 format
- Timestamps in ISO 8601 with timezone
- FK columns present and populated with the corresponding integer PKs
- One row per Session-Ops row (no duplicates) — except `m7_migration_slot_class_section_volunteer`, which must **unpivot** if Bubble stores volunteers as vol1/vol2 columns (decision #17): one output row per non-null volunteer
- `m7_migration_class_section` additionally computes `section_name` (slug) and `section_display_name` per decision #16

### dbt tests per model

Each model has associated tests:
- `not_null` on PK
- `unique` on PK
- `not_null` on required FKs
- `relationships` on FKs (references parent model's PK)
- `accepted_values` on enum-style columns (e.g., `user_role`, `holiday_reason`)

### Deployment

Deploy models to a dedicated dbt schema: `migration_m7`. Isolates from other dbt schemas so migration development doesn't affect other consumers.

## F-M7-5 — n8n workflow template

**Goal:** A reusable workflow template that all 20 table-specific workflows follow. This is the pattern each F-M7-6/7/8/9 workflow instantiates.

### Node structure

```
1. Manual Trigger / Schedule Trigger
   ↓
2. Set Migration Metadata
   - migration_batch_id: {{ uuid }}
   - table_name: "{{ table_name }}"
   - started_at: {{ $now }}
   ↓
3. Log Batch Start (n8n data table: migration_batch_log)
   ↓
4. GET Hasura /api/rest/migrate/{table_name}
   - Auth: Hasura JWT service token
   - Timeout: 60s
   - Retry on 5xx: 3 attempts, exp backoff
   ↓
5. Split In Batches (batch size: 50)
   - Splits response into chunks for logging clarity
   ↓
6. Loop over each row within batch:
   a. POST Session-Ops /api/internal/migrate/{table_name}/
      - Auth: Migration service token
      - Body: single row from Hasura response
      - Timeout: 30s
   b. IF success (2xx) → Log to migration_log (n8n data table)
      status: inserted/updated
   c. IF 4xx or 422 → Log to migration_log
      status: skipped
      reason: from response body
   d. IF 5xx → Stop workflow with error
      - Post to Slack: "Migration workflow stopped for {table_name} at row {pk}"
   ↓
7. Aggregate results
   - Count rows: inserted, updated, skipped
   ↓
8. Post batch summary to Slack (#session-ops-migration channel)
   - "✅ Migrated {table_name}: {inserted} new, {updated} updated, {skipped} skipped, batch_id={id}, duration={sec}s"
   ↓
9. Log Batch End (n8n data table)
```

### n8n data tables used

**`migration_batch_log`** — one row per migration workflow run
- batch_id (UUID)
- table_name
- started_at
- ended_at
- total_rows_fetched
- inserted_count
- updated_count
- skipped_count
- error_count
- status: running / completed / stopped

**`migration_log`** — one row per row migrated (or attempted)
- batch_id (UUID, FK to migration_batch_log)
- table_name
- source_pk
- action: insert / update / skip / error
- status_code
- error_message (nullable)
- warnings (JSON array)
- created_at

### Reusability

Each of the 20 table workflows is a copy of this template with:
- The `table_name` variable set
- The Hasura URL adjusted
- The Session-Ops URL adjusted

No custom logic per table — the template is generic. This is deliberate to keep the migration surface consistent and reduce per-workflow bugs.

## F-M7-6 through F-M7-9 — Migration workflows

These four features are the actual migration workflows, grouped by dependency layer.

**F-M7-6 (Layer 0):** program, academic_year, class, school_academic_year

Within this layer, `academic_year` must run and complete before `school_academic_year` (decision #13) — the master orchestration workflow sequences these two explicitly. `program` and `class` have no interdependencies and can run fully in parallel alongside `academic_year`. There is no `worknode` workflow — no such Session-Ops table exists. There is also no `subject` workflow — decision #18.

**F-M7-7 (Layer 1):** school_class, school_volunteer, school_session_details, school_holiday, class_section

`partner_worknode` is NOT part of this layer — it's already synced by the existing `sync_partner_worknode` command (decision #9).

**F-M7-8 (Layer 2):** child, child_class, child_class_section, child_removal_log, class_section_subject, child_subject, batch_child, child_program

**F-M7-9 (Layer 3):** slot, slot_class_section, slot_class_section_volunteer

Each workflow is a template instance (F-M7-5). Per-table peculiarities are handled in the corresponding dbt model (F-M7-3), not in the workflow.

Layer 1 workflows depend on Layer 0 completing successfully. Layer 2 on Layer 1. Layer 3 on Layer 2. n8n handles this either via manual sequencing (recommended for first runs) or a "master workflow" that triggers layers in order (recommended once stable).

## F-M7-10 — Data quality gate suite

**Goal:** After a migration workflow completes, run a suite of assertions to catch data corruption or logic bugs.

### Assertions per table

Each migration workflow ends with a "post-migration validation" step that runs these SQL assertions against Session-Ops Postgres:

1. **Row count check:** Session-Ops table row count matches `count(*)` from the corresponding Hasura endpoint's response.
2. **PK uniqueness:** No duplicate PKs in the migrated table.
3. **FK integrity:** All FK columns — including `school_id`-style raw-integer references per decision #15 — reference existing rows in parent tables.
4. **NOT NULL columns are not null:** As enforced by the DB, but double-check.
5. **Timestamp sanity:** No `created_at` in the future; no `updated_at` before `created_at`.
6. **Boolean sanity:** `is_active` and `removed` are proper booleans, not null.

### Cross-table assertions

After all workflows complete, additional assertions run:

- **Every child has exactly one active `child_class` row.** (R-class in aggregate — flags historical Bubble violations.)
- **Every child in an active bucket has exactly one active `child_class_section` row.** (R-bucket-membership in aggregate.)
- **Every active `slot_class_section` has at least one active `slot_class_section_volunteer`.** (R2 in aggregate.)
- **No `class_section` has more than 5 active `child_class_section` rows.** (R1 in aggregate — will fail for any Bubble bucket with >5 children; those are logged for manual review.)
- **Every `school_class`, `school_volunteer` (where set), `school_session_details`, `slot`, and `batch_child` row resolves to a valid `school_academic_year` row.** (Catches Layer 0 sequencing bugs — decision #13.)

### Reporting

The assertions run as a final n8n workflow (F-M7-10 itself) that queries Session-Ops via a dedicated `/api/internal/migrate/validate/` endpoint. Report format:

```
Migration validation summary — batch_id={id}
─────────────────────────────────────────

Table row counts:
  ✅ program: 3 (Hasura: 3)
  ✅ school_academic_year: 580 (Hasura: 580)
  ✅ child: 5847 (Hasura: 5847)
  ...

Cross-table checks:
  ✅ Every child has one active child_class row
  ⚠️  8 children have >1 active child_class_section rows
      [details of 8 violations logged]
  ⚠️  3 class_sections have >5 active children
      [details of 3 buckets logged]

Overall: PASS with warnings
```

Warnings don't block cutover but must be triaged (either fix in Session-Ops post-migration, or accept as historical data quality issues).

## F-M7-11 — Cutover playbook

**Goal:** A step-by-step operational plan for the day of the final cutover.

### T-14 days (2 weeks before cutover)

- Announce cutover date to CO/CHO/admin/volunteers via central communication (email + Slack).
- Announce Bubble read-only period after cutover (1-2 weeks).
- Confirm rollback authority (who decides if we abort cutover).
- Freeze non-critical Session-Ops feature work.

### T-7 days (1 week before cutover)

- **Full dry run** of migration end-to-end. Every table. In production Session-Ops instance (using production data from Bubble via warehouse).
- Compare Session-Ops row counts against Bubble row counts, table by table.
- Spot-check high-value data: latest 10 children, latest 10 slot-class assignments, all schools.
- Review data quality warnings from F-M7-10 assertions. Triage any critical issues.
- Fix any migration bugs uncovered. Re-run until clean.
- **Confirm** with Chetan / MAD leadership that cutover is a go for T-0.

### T-1 day (day before cutover)

- Announce final Bubble freeze window: "Please stop making changes in Bubble after 6pm today."
- Final data pipeline run overnight (Dalgo → warehouse → dbt).
- Confirm freshness of warehouse tables in the morning.
- All hands available T-0 morning.

### T-0 (cutover day)

**Hour 0:** Set Bubble to read-only mode (either Bubble config change or user comms).

**Hour 0-1:** Run all 20 migration workflows in order (Layer 0 → 3, with `academic_year` before `school_academic_year` inside Layer 0). Monitor n8n dashboards and Slack summary channel. Full pipeline should complete in 30-60 minutes.

**Hour 1:** Run F-M7-10 validation. Confirm all row counts match, no critical warnings.

**Hour 1-2:** Manual smoke test in Session-Ops:
- Log in as an admin, browse to 3 schools, verify children present.
- Log in as a CO, verify their school data.
- Verify the schedule view for 2 schools.
- Add a test child in Session-Ops, verify it persists.
- Delete the test child.

**Hour 2:** Advance Postgres sequences (F-M7-1 housekeeping SQL).

**Hour 2-3:** Announce Session-Ops is live. Redirect users from Bubble to Session-Ops (link change, email/Slack broadcast).

**Hour 3+:** Monitor for reports of issues. Have engineering standing by for 24 hours.

### T+1 to T+14 (rollback window)

- Bubble stays read-only. Users can consult it if needed but not modify.
- Any issues in Session-Ops → fix in Session-Ops (M6/M8a patterns).
- Continue user-onboarding communications.
- After 1-2 weeks of stable usage, officially retire Bubble.

## F-M7-12 — Rollback plan

**Goal:** If cutover reveals catastrophic issues in Session-Ops, revert users to Bubble.

### Rollback triggers (any one is sufficient)

- Session-Ops is down for > 2 hours during cutover day.
- > 20% of children data is corrupted or missing.
- Critical business rule violations that block CO/CHO from doing their work.
- FK integrity failures affecting > 5% of rows.
- Any data loss vs. Bubble's state at freeze time.

### Rollback procedure

**Hour 0:** Decision-maker (Tech-MAD or Chetan) invokes rollback.

**Hour 0:** Communicate to users: "We're reverting to Bubble temporarily. Please use the old app until further notice."

**Hour 0:** Un-freeze Bubble (allow writes again).

**Hour 0:** Point users back to Bubble URL (undo the link/redirect change).

**Post-rollback:** Root-cause the failure. Fix in Session-Ops. Retry cutover on a new date (typically 1-2 weeks later).

### What rollback does NOT do

- **Does not delete or roll back Session-Ops data.** The migrated data stays. Next cutover attempt just re-runs the migration (wiping and reloading).
- **Does not touch Bubble data.** Bubble is not modified during cutover; rollback just un-freezes it.
- **Does not require a database restore.** No Bubble backup restore needed — Bubble is the source of truth throughout.

Rollback is designed to be **cheap and reversible** — the whole point of Model 4 migration is that we can retry as many times as needed.

## Migration mode security

Migration mode is a powerful privilege — it can insert arbitrary data with relaxed validation. Security guardrails:

- **Dedicated service token** — separate from M8a token, only known to migration-mode callers (n8n and any manual test client)
- **Loader endpoints in `/api/internal/migrate/` namespace** — separate URL prefix, easy to audit in nginx/access logs
- **Token rotation on cutover completion** — after migration is done, rotate token to prevent accidental future use
- **No CO/CHO/admin access to migration endpoints** — enforced by service-token check, not user auth
- **Every request logged** — all migration requests appear in `migration_log` n8n data table with source_pk and timestamp

## What n8n needs to know about Bubble source PKs

n8n doesn't need to know anything special about Bubble's PKs. The dbt models handle the "get the right integer PK on each row" work. n8n just POSTs whatever it receives from Hasura.

## Sequence advancement post-migration

After all migration workflows complete, run this SQL to advance Postgres sequences past the max migrated PK. All 20 PK column names below were verified directly against `sessionops/models/` (checked 2026-07-15) — no guessing:

```sql
-- Advance sequences for all migrated tables
-- Run once, after all migrations complete, before opening Session-Ops for users

DO $$
DECLARE
    tables_pks TEXT[][] := ARRAY[
        ['program', 'program_id'],
        ['academic_year', 'academic_year_id'],
        ['class', 'class_id'],
        ['school_academic_year', 'school_academic_year_id'],
        ['school_class', 'school_class_id'],
        ['school_volunteer', 'school_volunteer_id'],
        ['school_session_details', 'session_id'],
        ['school_holiday', 'school_holiday_id'],
        ['class_section', 'class_section_id'],
        ['child', 'child_id'],
        ['child_class', 'child_class_id'],
        ['child_class_section', 'child_class_section_id'],
        ['child_removal_log', 'child_removal_log_id'],
        ['class_section_subject', 'class_section_subject_id'],
        ['child_subject', 'child_subject_id'],
        ['batch_child', 'batch_child_id'],
        ['child_program', 'child_program_id'],
        ['slot', 'slot_id'],
        ['slot_class_section', 'slot_class_section_id'],
        ['slot_class_section_volunteer', 'slot_class_section_volunteer_id']
    ];
    r TEXT[];
    seq_name TEXT;
    max_val BIGINT;
BEGIN
    FOR i IN 1..array_length(tables_pks, 1) LOOP
        r := tables_pks[i:i][1:2];
        seq_name := pg_get_serial_sequence(r[1], r[2]);
        IF seq_name IS NOT NULL THEN
            EXECUTE format('SELECT COALESCE(MAX(%I), 0) FROM %I', r[2], r[1]) INTO max_val;
            PERFORM setval(seq_name, GREATEST(max_val, 1));
            RAISE NOTICE 'Advanced sequence % to %', seq_name, GREATEST(max_val, 1);
        END IF;
    END LOOP;
END $$;
```

## Bubble read-only enforcement

Two options for freezing Bubble writes during cutover:

**Option B — Communication + trust:** Announce to CO/CHO/admin that Bubble is frozen from time T to time T+3 hours. Rely on their compliance. Verify by checking Bubble's audit log post-cutover for any writes during the freeze window.

**Recommendation:** Option A if available; Option B as fallback. Given MAD's team structure (small, well-communicated), Option B has been sufficient for similar transitions.

# Part 4 — Deviations and open questions

## Resolved decisions (confirmed at spec time, 2026-07-15)

- **`school_academic_year` added, migrated in Layer 0**, sequenced after `academic_year` specifically (decision #13). It was absent from the original draft despite being a hard FK dependency for 5 downstream tables.
- **`partner_worknode` dropped from scope entirely.** Confirmed: it already has its own sync (`sync_partner_worknode` management command → `run_partner_worknode_sync`), same pattern as `partner`/`user`. Treated as an external precondition (decision #9), not a migration target.
- **No standalone `worknode` table exists or is needed.** Confirmed: `worknode_id` is only ever a raw integer field on `PartnerWorknode` and `User`. There is no local `Worknode` model and none is needed for M7.
- **Net table count: 20**, not 21 (the original draft), 22 (an interim correction before `partner_worknode` was dropped), or 19 (before `child_removal_log` was found — decision #19).
- **`child_removal_log` added, Layer 2.** Found via a full audit of all 28 model classes in `sessionops/models/`; missing from every earlier draft. See decision #19.
- **Historical vs. active-only migration: migrate all rows, including soft-deleted/inactive.** Applies to `child_class`, `child_class_section`, `batch_child`, `child_program`, `school_volunteer`. Preserves audit history and gives M8a's realtime sync a complete prior-state picture.
- **`class_section`'s bucket-slug fields (`section_name`, `section_display_name`) are computed by dbt**, using the same normalization rule as `services/sections/slug.py::normalize_section_slug`, not by the loader endpoint (decision #16).
- **`batch_child` and `child_program` are real, already-built Session-Ops models** (`sessionops/models/child.py`) — confirmed to exist with straightforward FK shapes (`batch_child` → `school_academic_year` + `child`; `child_program` → `program` + `child`). No transformation ambiguity beyond the standard Bubble-source-column mapping deferred to the companion xlsx.
- **What happens if a Bubble row's PK matches an existing Session-Ops row? Upsert (update).** Confirmed — Session-Ops has no user-added data pre-cutover (staging only), so no risk of overwriting real user work.

## Open questions to resolve during build

- **`[TBD]` fields in `M7-Table-Specs.xlsx`:** Every table has some fields where the Bubble source column name is `[TBD]`. Resolve during dbt model construction.
- **What about Bubble rows with the same PK across different Session-Ops rows (e.g., soft-deleted + reactivated)?** Bubble's custom PK is guaranteed unique per table. Should not happen. If it does, DB unique constraint will reject the second insert.
- **`class` and `school_class` semantics:** `class` is the global catalog (1st-12th, see `sessionops/models/grade_class.py`). `school_class` is a per-school-per-academic-year instance (FKs to both `class` and `school_academic_year`). Confirm this understanding with the actual dbt models.

## Deviations from previous migration proposals

- **No source_ref column added to Session-Ops tables.** Because Bubble's custom integer PKs are directly usable, no extra column is needed.
- **No dedicated `migration_log` table on Session-Ops.** Migration audit lives in n8n data tables. Session-Ops schema stays clean.
- **No async/queue-based loader endpoints.** Data volume is small enough for sync endpoints.
- **No per-table auth tokens.** Single migration service token for all endpoints. Simpler; still isolated from user auth and M8a auth.

# Part 5 — Testing strategy

## Unit tests (per loader endpoint)

For each of the 20 endpoints:
- Happy path insert: new PK, all required fields → 201
- Happy path update: existing PK, changed fields → 200 with diff
- Missing required FK (including `school_id`-style raw-int references per decision #15) → 422 with `orphan_fk`
- Missing optional FK → 200 with warning, FK set to null
- Bad data (wrong type, oversized string) → 400
- Idempotent re-run: same payload twice → second call returns 200 with no changes
- Migration mode auth: valid token → success; invalid token → 401

## Integration tests (per workflow)

For each of the 20 n8n workflows:
- Mock Hasura response with 100 test rows
- Verify all 100 rows POST to Session-Ops
- Verify n8n data table `migration_log` has 100 rows
- Verify batch summary Slack message posted
- Verify workflow completes with expected counts
