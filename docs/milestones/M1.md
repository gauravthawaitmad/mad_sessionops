# Part 1 — Milestone Overview

## Production goal

At the end of M1, a user can:

1. Set their password via an email link sent through Brevo
2. Sign in with email + password
3. Reset a forgotten password (same flow as set)
4. See a list of schools (partners) scoped to their role
5. Click a school to view its info (read-only)
6. Sign out

Data is real — populated by a system cron task that pulls users and partners from Hasura's REST API every 6 hours. The whole thing runs in production at https://sessionops.makeadiff.in on EC2 behind nginx with Let's Encrypt TLS.

## Scope

### In scope

- **Password authentication:** set, login, forgot password (Brevo email)
- **RBAC scope filtering:** CO sees own schools, admin sees all, CHO sees empty list in M1
- **Hasura scheduled sync:** system cron runs every 6 hours, fetches users + partners (REST API, JWT auth)
- **School list page:** partner data displayed as schools, scope-filtered
- **School detail page:** Overview tab only; other tabs disabled placeholders
- **Logout flow**
- **Production deploy:** EC2 + nginx + certbot, RDS prod schema, single user model

### Out of scope (deferred)

- Google OAuth (M5)
- School configuration: classes, sections, holidays, session dates (M2)
- Children, volunteers, slots, scheduling (M3, M4)
- CHO active scope (M3 — needs volunteers)
- Real-time webhook sync (later)
- Sync admin dashboard (M5)
- Year progression (M5)
- Audit log model
- Bulk operations, exports, advanced filters
- Field-level change tracking with snapshots (M5)
- Pagination of Hasura sync (later)
- Celery / Redis (deferred to M5; M1 uses system cron)

> If something here turns out to be unexpectedly needed for M1, talk to the human first before adding scope.

## Architectural decisions for M1

**1. Partner IS the school.** Hasura has no separate school entity. Partner records hold school metadata (name, address, school_type, poc_*, mou_*). M1 has a single `Partner` model. The frontend calls them "schools" in UI; the model and code call them "partners" to match the source.

**2. `user_id` from Hasura is a numeric string with decimal suffix.** Example: `"2273058.000000000"`. The sync layer parses to integer before storing.

**3. The User table is already populated** (~4605 rows from prior import). M1 sync upserts: existing users update if their Hasura data changed, new users get inserted. Add `synced_at` column to track last successful sync per row.

**4. Sync is one-shot, no pagination, every 6 hours.** System cron triggers a Django management command. When volume grows or we need real-time, we revisit.

**5. No Celery / no Redis in M1.** Scheduling via system cron. Manual triggers via `python manage.py sync_hasura` command. Celery/Redis deferred to M5 when sync needs queueing semantics.

**6. Single auth method visible: email + password.** Google OAuth backend code from F01a stays in repo but the frontend doesn't expose it. M5 reactivates.

**7. `Partner.co_id` is NOT a DB-level FK to User.** `co_id` is a Hasura ID and may reference a user that hasn't synced yet. Use `db_constraint=False` per D024.

**8. Production schema fresh.** Create new `mad_sessionops_prod` database with `mad_sessionops_prod` schema. Apply migrations from scratch on prod.

# Part 2 — Features

## F-M1-1 — Password authentication

### What it does

- User on `/login` enters email + password → backend authenticates → JWT pair returned
- User clicks "Set password" or "Forgot password" → enters their email → Brevo emails them a link → they click and set a password
- Forgot password and Set password use the same flow
- Logout blacklists refresh token

### Schema — models and migrations

#### `PasswordResetToken` (NEW)

One row per user. UPDATE-in-place pattern. The same row is reused on every reset request — `token_hash`, `expires_at`, `consumed_at` all overwritten in place.

```python
class PasswordResetToken(SoftDeleteBaseModel):
    user           = OneToOneField(
                         User,
                         on_delete=PROTECT,
                         related_name="password_reset_token",
                     )
    token_hash     = CharField(max_length=64, db_index=True)  # SHA-256 hex
    expires_at     = DateTimeField()
    consumed_at    = DateTimeField(null=True, blank=True)
    requested_at   = DateTimeField()
    requested_ip   = GenericIPAddressField(null=True, blank=True)

    class Meta:
        db_table = "password_reset_token"
```

**Token lifecycle:** user requests reset → `update_or_create` with new hash, new expiry, `consumed_at=None`. User clicks link → backend hashes the URL token, looks up by hash, validates `expires_at > now` and `consumed_at IS NULL`. After successful set → `consumed_at=now()`. The same row gets overwritten on the next reset request.

#### `EmailRateLimit` (NEW)

Insert-only audit log. Does NOT inherit `SoftDeleteBaseModel`.

```python
class EmailRateLimit(models.Model):
    id        = BigAutoField(primary_key=True)
    key       = CharField(max_length=255, db_index=True)
                # "ip:1.2.3.4" or "user_login:foo@bar.com"
    purpose   = CharField(max_length=32)
                # "password_reset" — extensible
    sent_at   = DateTimeField(auto_now_add=True, db_index=True)

    class Meta:
        db_table = "email_rate_limit"
        indexes = [models.Index(fields=["key", "sent_at"])]
```

**Rate limit check:** count rows where `key=<ip|user_login>` AND `sent_at > now() - 1h`. If count >= 10, raise `RateLimitError`. The 10/hour limit is a code constant in `services/auth/password.py`, not configurable.

#### `User` (modify)

Add field: `synced_at: DateTimeField(null=True, blank=True)` — tracks when this row was last refreshed from Hasura.

### Backend — services

#### `services/email/brevo.py`

`send_email(to, template_id, variables) -> bool`

- Calls Brevo's transactional API
- Reads `BREVO_API_KEY`, `BREVO_FROM_EMAIL`, `BREVO_FROM_NAME` from env
- On Brevo API failure: catches exception, logs to Sentry, returns False (caller treats email as fire-and-forget)
- Never logs the email address or template variables at INFO level (PII)

#### `services/auth/password.py`

`request_reset(user_login, request_ip) -> None`

1. Rate limit check (10/hour per IP and per user_login)
2. Look up User by lowercased user_login
3. If not found: silently return success + still insert IP-keyed rate limit row (prevents enumeration via rate-limit responses)
4. If found and ineligible (inactive or no allowed roles): same — return success silently
5. If found and eligible: generate 32 bytes random → URL-safe base64 → raw token (~43 chars). SHA-256 hash.
6. `update_or_create` PasswordResetToken row with new hash, `expires_at = now + 1h`, `consumed_at = None`
7. Compose email link: `{FRONTEND_URL}/auth/set-password?token={raw_token}`
8. Send via Brevo
9. Insert rate limit rows (IP + user_login)

`set_password_with_token(token, password, password_confirm) -> User`

1. Validate `password == password_confirm`; password length 8-128
2. Hash incoming token (SHA-256)
3. Look up PasswordResetToken: `token_hash=hashed, consumed_at__isnull=True, expires_at__gt=now()`
4. If not found: raise `AuthenticationError` (invalid or expired)
5. Re-validate user is_active and has allowed roles. Raise if not.
6. Atomic transaction: hash password with Argon2id, `update_or_create` UserAuth (auth_type=password, auth_identifier=user_login.lower(), password_hash=hash), mark token consumed.

`complete_password_login(user_login, password) -> tuple[User, str, str]`

1. Look up User by lowercased user_login
2. Validate is_active and has allowed roles. If not: raise `AuthenticationError` (generic)
3. Look up active UserAuth row: `user=user, auth_type=password, is_active=True`
4. If not found: raise `AuthenticationError` (no password set yet — same generic message)
5. Verify password with Argon2id (`django.contrib.auth.hashers.check_password`). If fails: raise.
6. Update `User.last_login_at = now()` and `UserAuth.last_used_at = now()`
7. Issue JWT pair via simplejwt and return

`verify_token_validity(token) -> bool`

Hashes the token, looks up the row. If exists with `consumed_at IS NULL` and `expires_at > now`, returns True. Else False. Used by the GET pre-flight endpoint. No state changes.

### Acceptance criteria

1. New user with no password row can request a reset, receive email, click link, set password, and log in
2. Existing user can request a reset, set a new password (overwriting the previous one), and log in
3. Used token cannot be reused (returns 401)
4. Expired token cannot be used (returns 401)
5. Wrong password returns generic 401 — does not reveal whether user exists
6. Inactive user gets generic 401 (R12)
7. User with no allowed roles (e.g., "Academic Support" only) gets generic 401 (R11)
8. Rate limit: 11th request within an hour from same IP returns 429
9. Rate limit: 11th request within an hour for same user_login returns 429
10. Login updates `User.last_login_at` and `UserAuth.last_used_at`
11. Logout blacklists the refresh token; subsequent `/refresh` with same token returns 401

## F-M1-2 — Hasura scheduled sync

### What it does

- System cron task runs every 6 hours
- Triggers Django management command: `python manage.py sync_hasura`
- Pulls users and partners from Hasura's REST API in one job
- Upserts into local DB (creates new rows, updates changed rows)
- Soft-deactivates partners where `crm_partner_removed=true` in Hasura
- Logs each sync run with timing, counts, status, errors

**What it does NOT do (yet):** real-time updates (M5 webhooks), field-level change tracking with snapshots (M5), admin UI for sync history (M5), pagination (later when volume grows).

### Backend — services

#### `services/hasura/client.py`

`fetch_users() -> list[dict]`

- `GET https://hasura.makeadiff.in/api/rest/user_data`
- Authorization header: `Bearer <HASURA_API_JWT>`

### Backend — management command

#### `python manage.py sync_hasura`

`sessionops/management/commands/sync_hasura.py`

Internally calls `services/sync.py::run_sync()`.

**Run flow:**

1. Create SyncRun row with `status="running"`
2. Try: `fetch_users()` → upsert each → track counts
3. Try: `fetch_partners(...)` → upsert each → track counts → handle `crm_partner_removed`
4. On success: SyncRun `status="success"`, `completed_at` = now
5. On any exception: SyncRun `status="failed"`, `error_message`, log to Sentry, re-raise

**Idempotency:** running the command twice produces the same final state. Upsert keys: `User.user_id`, `Partner.partner_id`. No blind inserts.

**Bounds:** M1 fetches all rows in a single API call. ~5000 users + ~580 partners fits comfortably. If Hasura starts returning >50k rows, revisit pagination.

### Acceptance criteria

1. Running `python manage.py sync_hasura` against dev Hasura completes without errors
2. First run on a fresh DB populates Partner table

## F-M1-3 — RBAC scope filtering

### What it does

A reusable scope helper takes the current User and returns a queryset filter. The school list and detail endpoints apply it. Frontend doesn't reimplement these rules — backend filters server-side.

### Scope rules in M1

| Role | Schools visible | Notes |
|---|---|---|
| Function Lead, Project Lead, Project Associate | All partners | Admin scope |
| CXO | All partners | Treated as admin scope in M1 |
| CO Full Time, CO Part Time | Where `partner.co_id == user.user_id` | Their assigned schools only |
| CHO | None (empty list) | Volunteers don't exist in M1; M3 enables real CHO scope |
| Other roles (e.g. Wingman, Fellow, Academic Support) | Cannot log in | Per R11 — login is gated |

### Backend — services

#### `services/rbac/scope.py`

`schools_visible_to(user: User) -> QuerySet`

- Reads user's roles via existing `get_allowed_roles(user.user_role)`
- Returns a `Partner.objects.filter(...)` queryset
- For admin scope: `Partner.objects.all()`
- For CO: `Partner.objects.filter(co_id=user.user_id)`
- For CHO: `Partner.objects.none()`

`can_view_school(user: User, partner: Partner) -> bool`

- Single-school visibility check, used by detail endpoint
- Admin scope: True. CO: `partner.co_id == user.user_id`. CHO: False.

### Acceptance criteria

1. CO Full Time user sees only partners where `co_id` matches their `user_id`
2. Function Lead sees all partners
3. CHO sees empty list
4. CXO sees all partners (admin scope)
5. Scope is applied server-side; frontend cannot bypass via query manipulation
