# Milestone 1 — Auth + School Visibility

**Status:** in progress
**Duration:** 2 weeks (~9 build days, ~3-4 stabilize days)
**Production domain:** https://sessionops.makeadiff.in

## What ships at the end of M1

A user can:
1. Set their password via an email link sent through Brevo
2. Sign in with email + password
3. Reset a forgotten password (same flow as set)
4. See a list of schools (partners) scoped to their role
5. Click into a school to view its info (read-only)
6. Sign out

The data is real — populated by a Celery beat task that pulls users and partners from Hasura's REST API every 6 hours.

The whole thing runs in production at https://sessionops.makeadiff.in on EC2 behind nginx with Let's Encrypt TLS.

## Key architectural decisions for M1

These are foundational decisions baked into M1. Read before designing models or services.

1. **Partner IS the school.** Hasura has no separate `school` entity. Partner records hold school metadata (name, address, school_type, poc_*, mou_*). M1 has a single `Partner` model. The frontend calls them "schools" in the UI; the model and code call them "partners" to match the source.

2. **`user_id` from Hasura is a numeric string with decimal suffix.** Example: `"2273058.000000000"`. The sync layer parses this to integer before storing.

3. **The User table is already populated** (4605 rows from prior import). M1 sync upserts: existing users update if their Hasura data changed, new users get inserted. Add a `synced_at` column (note: we'll call it `synced_at` not `sync_datetime` for naming consistency with `created_at`/`updated_at`) to track last successful sync per row.

4. **Sync is one shot, no pagination, every 6 hours.** When the volume grows or we need real-time, we revisit. M1 keeps it simple.

5. **Redis IS needed in M1** because Celery beat schedules the sync task. Redis runs as a Docker container (dev) or a managed instance / standalone service (prod TBD — probably Docker on the same EC2 for M1, ElastiCache later if scale demands).

6. **Single auth method visible in M1: email + password.** The Google OAuth backend code from F01a stays in the repo but the frontend doesn't expose a Google button. M5 brings it back.

7. **Existing `mad_sessionops_dev` schema is the dev source of truth.** Production gets a fresh `mad_sessionops_prod` schema in a new `mad_sessionops_prod` database (RDS).

## Models in M1

Five models. All inherit from `SoftDeleteBaseModel` unless noted.

### 1. `User` (already exists — extends what's there)

Currently has: `user_id`, `user_login`, `user_role`, `email`, `display_name`, `is_active`, `last_login_at`, plus the SoftDeleteBaseModel fields.

**M1 adds:**
- `synced_at: DateTimeField(null=True, blank=True)` — when this row was last refreshed from Hasura

Migration: simple `AddField`.

The Hasura → User field mapping for sync (M1 only updates these fields on existing users; creates new users with the same fields):

| Hasura field | User field | Notes |
|---|---|---|
| `user_id` | `user_id` | Strip `.000000000`, parse to int |
| `user_login` | `user_login` | Lowercase before storing |
| `user_display_name` | `display_name` | |
| `email` | `email` | Lowercase |
| `user_role` | `user_role` | Comma-separated string, store verbatim |
| `user_created_datetime` | `created_at` | Parse to UTC datetime — but only on first insert; don't overwrite on subsequent syncs |
| `user_updated_datetime` | `updated_at` | Update each sync |
| (other Hasura fields: city, state, contact, center, reporting_manager_*, added_by) | NOT stored in M1 | Out of scope for M1; add columns when a feature needs them |

`is_active` is NOT touched by sync in M1. Hasura doesn't send an active flag in the response shown. Users disabled in Hasura need a different signal (presence/absence in the response). For M1, sync DOES NOT deactivate users that disappear from the response — defer this to M5 when sync logic gets serious. This means a stale user in our DB stays active until manually fixed. Acceptable risk for M1.

### 3. `Partner` (NEW)

Represents both the partner relationship and the school. Mapped from Hasura's `prod_external_apps_partner_data`.

```python
class Partner(SoftDeleteBaseModel):
    # Identity (from Hasura)
    partner_id            = BigIntegerField(unique=True, db_index=True)  # Hasura's partner_id
    partner_name          = CharField(max_length=255)
    
    # CO assignment
    co_id                 = BigIntegerField(null=True, blank=True, db_index=True)  
    # Note: NOT a ForeignKey to User. co_id is a Hasura ID and may reference a 
    # user that hasn't synced yet. We resolve to User at query time, not via DB FK.
    # This is a deliberate db_constraint=False scenario per D024.
    co_name               = CharField(max_length=255, null=True, blank=True)
    
    # School info
    address_line_1        = TextField(null=True, blank=True)
    address_line_2        = TextField(null=True, blank=True)
    city                  = CharField(max_length=100, null=True, blank=True)
    city_id               = IntegerField(null=True, blank=True)
    state                 = CharField(max_length=100, null=True, blank=True)
    state_id              = IntegerField(null=True, blank=True)
    pincode               = IntegerField(null=True, blank=True)
    school_type           = CharField(max_length=100, null=True, blank=True)
    partner_affiliation_type = CharField(max_length=100, null=True, blank=True)
    
    # Point of contact
    poc_name              = CharField(max_length=255, null=True, blank=True)
    poc_email             = CharField(max_length=255, null=True, blank=True)
    poc_designation       = CharField(max_length=255, null=True, blank=True)
    poc_contact           = CharField(max_length=50, null=True, blank=True)
    
    # MOU
    mou_sign_date         = DateField(null=True, blank=True)
    mou_start_date        = DateField(null=True, blank=True)
    mou_end_date          = DateField(null=True, blank=True)
    mou_url               = TextField(null=True, blank=True)
    
    # Lifecycle
    converted             = BooleanField(default=False)
    crm_partner_removed   = BooleanField(default=False)
    latest_conversion_stage = CharField(max_length=50, null=True, blank=True)
    lead_source           = CharField(max_length=100, null=True, blank=True)
    date_of_first_contact = DateTimeField(null=True, blank=True)
    
    # Counts (denormalized from Hasura — M1 just stores what comes; doesn't compute)
    confirmed_child_count = IntegerField(null=True, blank=True)
    total_child_count     = IntegerField(null=True, blank=True)
    classes               = TextField(null=True, blank=True)  # raw from Hasura
    
    # Sync tracking
    partner_created_date  = DateTimeField(null=True, blank=True)  # from Hasura
    partner_updated_date  = DateTimeField(null=True, blank=True)  # from Hasura
    synced_at             = DateTimeField(null=True, blank=True)  # our last sync time
    
    class Meta:
        db_table = "partner"
        indexes = [
            models.Index(fields=["co_id"]),
            models.Index(fields=["partner_updated_date"]),
        ]
```

**Important:** when sync sees `crm_partner_removed=true` in Hasura, the local row gets `is_active=False` (soft-delete via `SoftDeleteBaseModel`). When `crm_partner_removed=false`, the local row's `is_active=True`. This is the only signal we have for "this partner is no longer active in MAD's records."

### 4. `PasswordResetToken` (NEW)

One row per user. UPDATE-in-place pattern.

```python
class PasswordResetToken(SoftDeleteBaseModel):
    user           = OneToOneField(User, on_delete=PROTECT, related_name="password_reset_token")
    token_hash     = CharField(max_length=64, db_index=True)  # SHA-256 hex
    expires_at     = DateTimeField()
    consumed_at    = DateTimeField(null=True, blank=True)
    requested_at   = DateTimeField()
    requested_ip   = GenericIPAddressField(null=True, blank=True)
    
    class Meta:
        db_table = "password_reset_token"
```

Token lifecycle:
- User requests reset → row created (or updated in place if exists) with new hash, new expiry, `consumed_at=None`
- User clicks link → backend hashes the URL token, looks up by hash, validates `expires_at > now` and `consumed_at IS NULL`
- After successful set → `consumed_at=now`. Row stays (audit), but token is unusable.
- Next reset request from same user → same row gets overwritten

### 5. `EmailRateLimit` (NEW)

Insert-only rate limit log.

```python
class EmailRateLimit(models.Model):
    # Note: NOT inheriting SoftDeleteBaseModel — this is insert-only audit data
    id        = BigAutoField(primary_key=True)
    key       = CharField(max_length=255, db_index=True)  # "ip:1.2.3.4" or "user_login:foo@bar.com"
    purpose   = CharField(max_length=32)  # "password_reset" — extensible for future
    sent_at   = DateTimeField(auto_now_add=True, db_index=True)
    
    class Meta:
        db_table = "email_rate_limit"
        indexes = [
            models.Index(fields=["key", "sent_at"]),
        ]
```

Rate limit check: count rows where `key=<ip|user_login>` AND `sent_at > now() - 1h`. If `>= 10`, raise `RateLimitError`.

(M1 specifically uses 10/hour per your direction. Code constant in `services/auth/password.py`.)

### 6. `SyncRun` (NEW)

Logs every Celery sync run for visibility.

```python
class SyncRun(models.Model):

    started_at      = DateTimeField(auto_now_add=True, db_index=True)

                          ("running", "Running"),
                          ("success", "Success"),

    users_created   = IntegerField(default=0)
    users_updated   = IntegerField(default=0)
    partners_fetched = IntegerField(default=0)
    partners_created = IntegerField(default=0)
    partners_updated = IntegerField(default=0)

```

## Endpoints in M1

### Auth — password (NEW in M1)

- **`POST /api/auth/password/login`** — public. Body: `{user_login, password}`. Returns `LoginResponseSchema`. Errors: 401 generic, 400 validation.
- **`POST /api/auth/password/request-reset`** — public. Body: `{user_login}`. Returns 202 `{message: "If an account exists, an email has been sent."}` always (no enumeration). Errors: 429 if rate limit hit.
- **`POST /api/auth/password/set`** — public. Body: `{token, password, password_confirm}`. Returns 204. Errors: 401 (token invalid/expired/used), 400 (password validation fails).
- **`GET /api/auth/password/verify-token?token=<token>`** — public. Returns `{valid: true|false}`. Used by frontend's set-password page to pre-validate before showing the form.

### Auth — existing (built in F01a, kept)

- `POST /api/auth/refresh` — kept (12h access expiry means refresh is real)
- `POST /api/auth/logout` — kept
- `GET /api/auth/me` — kept
- `POST /api/auth/google/callback` — exists in code but **not exposed in any frontend route in M1**. Either disable the URL pattern or just don't link to it. M5 reactivates.

### Schools (NEW in M1)

- **`GET /api/schools/`** — auth required. Returns scope-filtered list. Query params: `?search=<text>` for name/city/state filter.

  Response schema:

### Key service contracts

**`services/email/brevo.py::send_email(to, template_id, variables)`** — calls Brevo's API. Reads `BREVO_API_KEY` from env. Reads `BREVO_FROM_EMAIL` and `BREVO_FROM_NAME`. On failure: catches exception, logs to Sentry, returns silently (caller treats email as fire-and-forget).

**`services/auth/password.py::request_reset(user_login, request_ip)`** — full logic per spec. Rate limit check (10/hour per IP and per user_login), upsert PasswordResetToken, send via Brevo. Returns success regardless of whether user exists.

**`services/auth/password.py::set_password_with_token(token, password, password_confirm)`** — validates password, hashes token with SHA-256, looks up token, validates expiry/usage, upserts UserAuth row with `auth_type="password"`, marks token consumed.

**`services/auth/password.py::complete_password_login(user_login, password)`** — looks up User by `user_login` (case-insensitive), validates `is_active` and allowed roles, looks up active password UserAuth row, verifies password with Argon2id, issues JWT pair.

**`services/hasura/client.py::fetch_users()`** — GET `https://hasura.makeadiff.in/api/rest/user_data` with JWT auth header. Returns parsed list. Handles `user_id` string-to-int conversion.

**`services/hasura/client.py::fetch_partners(updated_after)`** — GET with `?updated_after=<datetime>` param. For M1, pass a hardcoded older date like `2006-01-01T00:00:00` to get full data each run.

**`services/rbac/scope.py::schools_visible_to(user) -> QuerySet`** — returns `Partner.objects.filter(...)` based on user's roles:
- Admin scope (Function Lead, Project Associate, Project Lead): all partners
- CXO: all partners (treated as admin scope for visibility)
- CO Full Time / CO Part Time: `co_id == user.user_id`
- CHO: `Partner.objects.none()` for M1 (volunteers don't exist yet)

## Celery tasks in M1
sessionops/tasks/
└── sync.py                     # NEW
├── sync_hasura             # main entry — fetches users + partners, upserts each
├── sync_users              # internal helper
└── sync_partners           # internal helper

**Beat schedule** (in settings.py):

```python
CELERY_BEAT_SCHEDULE = {
    "sync_hasura_every_6_hours": {
        "task": "sessionops.tasks.sync.sync_hasura",
        "schedule": crontab(minute=0, hour="*/6"),  # 00:00, 06:00, 12:00, 18:00 UTC
    },
}
```

**`sync_hasura` flow:**
1. Create SyncRun row (status="running")
2. Call `fetch_users()` → upsert into User table; track counts
3. Call `fetch_partners(updated_after=earliest_date)` → upsert into Partner table; soft-delete partners where `crm_partner_removed=true`; track counts
4. Update SyncRun: completed_at, status, counts
5. On exception: SyncRun.status="failed", error_message, log to Sentry, re-raise (Celery retries with exponential backoff up to 3 attempts)

**Idempotency:** running the task twice produces the same final state. Upsert keys: `User.user_id`, `Partner.partner_id`. No blind inserts.

**Bounds:** M1 fetches all rows in one call (no pagination per your direction). For ~5000 users and ~580 partners (rough scale based on what we've seen), this fits comfortably in memory and a single transaction. If response sizes grow significantly, we add pagination later.

   - Architecture decisions arise that this doc doesn't answer

   - Style or formatting issues
