# Session-Ops Backend — Claude Code Orientation

This file is read at the start of every Claude Code session. Read it in full before touching any code.

## What this repo is

Session-Ops is MAD's internal school operations platform. This repo is the Django + Ninja backend. Frontend lives in a separate repo: `mad-sessionops-frontend`.

The product manages the full lifecycle of MAD's school partnerships: City Officers (COs) set up classes, enroll children, assign volunteers, and schedule teaching slots. External user data syncs from Hasura via webhooks. Admin monitors sync health and runs annual year-progression.

## Stack

- Django 4.2
- Django Ninja 1.0+ (not DRF)
- PostgreSQL 14 on AWS RDS (ap-south-1)
- Celery 5.3+ with Redis broker
- JWT auth via djangorestframework-simplejwt with custom Ninja middleware
- Pydantic v2 schemas
- uv for dependency management
- Python 3.12+

## Feature work specifically

If you are building a feature, the workflow is:

1. Read `docs/FEATURE_PLAN.md` to confirm scope and dependencies.
2. Read `docs/features/FXX-name.md` for the feature you're building. Every section is required reading — sections 8 (business rules), 10 (acceptance criteria), and 11 (test scenarios) are non-negotiable.
3. Read `docs/UI_REFERENCE.md` if the feature has frontend.
4. Reference prototype screenshots in `docs/ui-prototype/` only as called out in the feature doc.
5. Build. Update the feature doc's section 14 (Done log) as you go.
6. When complete, update `docs/PROGRESS.md` and the feature's status in `docs/FEATURE_PLAN.md`.

Do not skip the feature doc. If a feature doc is missing or unclear for what you're about to build, stop and clarify with the human first.

## Non-negotiable rules

These are enforced rules, not guidelines. Every one has business rationale in `docs/BUSINESS_RULES.md`. Do not violate them, even temporarily.

1. **Soft delete only.** No hard deletes anywhere. Every model that can be deactivated has an `is_active` or `is_deleted` field and a mandatory `removed_reason` if applicable.
2. **Business rule enforcement is at the service layer, not the view and not the DB.** Max-5-children, 1-volunteer-per-school, etc. are all Python validations in `sessionops/services/`. Views call services; services enforce rules; models store data.
3. **Queries filter `is_active=True` / `is_deleted=False` by default.** Admins bypassing this must do so explicitly (e.g., `.all_with_deleted()`).
4. **Never use Django's built-in User model.** `sessionops.models.User` is the custom user. Importing from `django.contrib.auth.models` is a bug.
5. **RBAC is enforced on every endpoint.** No unauthenticated write paths except `/auth/*` endpoints. No endpoint returns data outside the caller's role scope.
6. **Single source of truth for academic year.** There is one globally active academic year at any time. `School.active_year` is denormalized but `AcademicYear.is_active=True` is the canonical source.
7. **Removal reason is mandatory when deactivating a child.** Not optional. Enforced at the service layer before `is_active=False` is set.

## Architectural patterns to follow

- **Views are thin.** They parse input, call a service, return output. No business logic.
- **Services are the unit of testing.** Tests target services with in-memory fixtures; view tests are integration-level only.
- **Schemas are Pydantic v2.** Use `field_validator`, not `@validator`. Use `model_config`, not `Config`.
- **Errors are typed.** Raise `AuthenticationError`, `PermissionDenied`, `ValidationError`, `NotFound`, `ConflictError` — all defined in `sessionops/exceptions.py`. A Ninja exception handler maps them to HTTP responses.
- **Celery tasks are idempotent.** A task running twice produces the same result as running once. No exceptions.
- **Settings read from env via `os.environ`**, with sane defaults for dev. Secrets never have dev defaults — if missing, raise at import time.

## Rules for modifying docs

Docs are code. They lie if they drift. Every PR that changes behavior updates the relevant doc in the same commit.

- Adding a model → update `docs/DATA_MODEL.md`
- Adding an endpoint → update `docs/API_CONVENTIONS.md` only if it establishes a new pattern; otherwise the OpenAPI spec is sufficient
- Adding a business rule → update `docs/BUSINESS_RULES.md`
- Making a significant choice → add entry to `docs/DECISIONS.md`
- Completing a user story → update `docs/PROGRESS.md`

If a doc contradicts the code, **the code is assumed correct and the doc is wrong** — fix the doc. If in doubt, ask the human.
